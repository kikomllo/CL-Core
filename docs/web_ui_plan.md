# Web front end plan

Why: Qt's QSS fights us (smooth-border engine, skin recolouring, scaler injector, responsive layout hacks). A web UI gets rounded borders, CSS variables for skins, grid/rem layout, canvas/SVG/WebGL and `xterm.js` for free.

## Architecture
- `src/clWebUI.py` (aiohttp, 127.0.0.1:8765): serves `web/` and `assets/{fonts,icons,themes}`, and bridges one paho connection to a WebSocket `/ws`. Frames: client sends `{sub:[topics]}`, `{act:"spotify.control", k:{...}}` (an `actions.json` action, validated by `ActionRouter.prepare`), `{pub:topic, p:payload}`; server sends `{t:topic, p:text}` and replays the last message per topic to a new tab. Cross-origin WebSockets are refused. The system Mosquitto config is not touched (needs admin).
- `web/` is plain ES modules, no build step. `js/bridge.js` (topics in/out), `js/state.js` (orb state machine, ported from `MqttThread.evaluate_state`), `js/orb.js`, `js/clock.js`, `js/skin.js`, `js/ui.js` (icons + draggable/resizable windows, layout saved per window as fractions of the viewport), one `js/<widget>.js` per widget, `js/main.js` (dock + start-up). `--u` is the fluid unit (`min(long/1920, short/1080)`); every size is `calc(N * var(--u))`.
- **Stylesheet: one small file per part of the UI in `web/css/`** (`00-fonts`, `01-tokens`, `02-base`, ..., `10-media`, `11-lyrics`, `19-calendar`, `21-logs`, `23-claude`...). The number prefix is the cascade order. `clWebUI` joins them (`src/utils/clWebCss.py`) into the one `/style.css` both pages link and recolours that, so `index.html`, `widget.html` and the skins are unchanged; `tests/webcss.py` gives the tests the same joined text. A new part of the UI gets its own file; a rule that must beat another of the same specificity goes in a later file (`20-scrollbar-edge.css` is deliberately after the modules and the calendar). Older notes below that say `style.css` mean this bundle.
- Run: `python src/clWebUI.py`, open `http://127.0.0.1:8765/` (`?open=media` opens a widget at start).

## Shell (done: Electron)
`shell/` is the desktop app: ONE transparent frameless Electron window showing the page served by `clWebUI.py`. Chosen over Tauri because Tauri needs Rust + the MSVC build tools (not installed, multi-GB on each machine) while Node is already here; Electron gives true transparency, click-through, always-on-top and multi-monitor on Windows and Linux with one pinned dependency (`shell/package.json`, Electron 45.2.3).
- **Modes, like the Qt dashboard.** `overlay`: a 200x200 box (it was 200x400 like the Qt one, which put the orb 200 px up the screen instead of in the corner) (scaled by the monitor, 20 px in from the bottom right of the primary monitor's work area), always on top, click-through, unfocusable, the page shows only the orb (`html[data-mode="overlay"]` in `style.css`; the unit comes from the monitor's size, not the small window's). `fullscreen`: the whole dashboard on the monitor the pointer is on (else the saved one), an ordinary interactive window. A cold start opens the overlay; `JARVIS_REBOOT=1` (a supervisor restart) reopens the saved mode (`data/shell_state.json`). `jarvis/sys/ui_control` (`set_overlay` / `set_fullscreen`: the keybinds, tray, voice) is handled by the page (`web/js/shell.js`), which asks the shell over IPC (`preload.js` -> `window.jarvisShell`); in a plain browser tab `window.jarvisShell` does not exist and the page ignores those messages. `clWebUI.py` never replays `ui_control` to a page that opens later (`NO_REPLAY`), or a stale `set_overlay` would flip the mode at start.
- **The overlay shows only while the orb does.** Like the Qt overlay, the orb is at opacity 0 (and shrunk) at rest, and the page tells the shell (`jarvisShell.setVisible`, sent from an event, because a hidden window stops its frame loop) so the window is *hidden* while nothing shows: no frames, no compositing, nothing on screen. The bloom is held to the window's size in the overlay (`orb-model.js` `bloomRadius`): a 170 px glow in a 200 px box reached the window's edge, was cut there, and showed the rectangle; verified by rendering the overlay speaking and checking alpha 0 on all four edges. Tests: `tests/test_webOrb.py`. `JARVIS_SHELL_EVAL=<js>` runs a script in the page before a test screenshot (e.g. to put the orb in a state without touching MQTT).
- **Stacking order (bottom to top):** orb, clock, lyrics (`z-index: 5`), the windows (`#widgets` is a stacking context and needs its own `z-index: 10`, or the lyrics paint over every window; `ui.js` `zTop`, from 11 inside it), the dock (5000), the calendar drawer (5500). The lyrics were at 4000, over every window.
- **Files.** `shell/geometry.js` (pure, tested: `tests/test_shellGeometry.py`), `shell/main.js` (window, modes, state, single-instance lock that waits for the previous shell after a restart, parent watchdog), `shell/preload.js`, `src/clShell.py` (the supervisor's launcher: starts Electron, relays its log, announces `module_ready` as "desktop shell", exits with it), `src/utils/clShellSupport.py` (finding the binary, the clean environment, `choose_ui`; tests: `tests/test_clShell.py`).
- **Supervisor.** `modules.json`: `"Desktop Shell": true`, `"UI": false` (the Qt dashboard). If the shell is not installed (no Node, `npm install` failed) `choose_ui` turns the Qt dashboard on instead, so a machine is never left without a UI. `boot.py` runs `npm install` in `shell/` once. Flip the two flags to go back to Qt. To run it by hand: `python src/clShell.py` (needs `clWebUI.py` running; it retries until the server answers).
- **Gotchas.** VS Code (so any terminal or Claude Code session started from it) sets `ELECTRON_RUN_AS_NODE=1`, which makes Electron run as plain Node with no window: `build_env` strips it. The shell polls `JARVIS_SHELL_PARENT` every 2 s and quits when the launcher is gone, because the supervisor's terminate on Windows kills only the launcher. Render-only mode for tests and screenshots: `JARVIS_SHELL_TEST=1 JARVIS_SHELL_MODE=overlay|fullscreen JARVIS_SHELL_SHOT=<abs png>` (nothing is shown; prints `[SHELL-TEST] {...}`).
- **Cost (measured, Windows, fullscreen at rest).** 4 Chromium processes, ~300 MB private, ~1 % of a core (the orb idles at 8 Hz); the Qt dashboard process is ~130 MB. Merging the GPU and network processes into the main one halves the process count but saves no memory (tried, reverted: a GPU crash would take the shell down). The V8 heap is capped at 384 MB and the page is the only renderer.

## Web server access log (off)
aiohttp's per-request access log was on: one stdout line per request (`GET /api/log?pos=...`, every icon, the 3 s settings poll), which the supervisor writes to `logs/latest_run.log`, which the Live Logs widget polls through `GET /api/log` and shows, so every poll created the line the next poll displayed (an endless stream of `[CONFIG] 127.0.0.1 ... "GET /api/log..."`). `clWebUI.access_log()` returns `None` unless `JARVIS_WEB_ACCESS_LOG=1`; warnings and errors still log. Tests: `TestAccessLog` in `tests/test_clWebUI.py`.

## Window minimum size (web)
A widget's smallest size is **measured from its content** (`ui.js` `fitMin`), not a number each widget guessed (the fixed `minW`/`minH` are gone): the user can resize a window to any size at which the content still fits, and no smaller. The content of every widget scrolls inside `.win-body` and several have their own scrolling regions, so the measurement works like this: (1) the scrolling regions (`ELASTIC`: lists and pages `.mod-list, .rem-grid, .set-pages`, the tab strip `.tabs-pill`, the terminals `.t-screen, .cl-screen`) are replaced by a small floor (200 x 72 design px for a list, 350 x 140 for a terminal, any width for the tab strip), since a list or a log can be any size; (2) text cut with an ellipsis is excluded from the width (`contain: inline-size`), so a long song title never sets the minimum; (3) the window is sized `min-content` x `auto` and read, and the DOM is restored in the same task (nothing paints in between). It runs when a window opens, again 1.5 s later (data arrives after the first paint), and at the start of every resize drag. Window titles, headings and buttons never wrap (`white-space: nowrap`), so a minimum always shows them whole. Verified by rendering all nine widgets at their measured minimums in one grid in the desktop shell: media 214x259, lights 222x231, to-do 222x303, notes 222x174, reminders 222x167, settings 222x211, updates 222x235, Claude 368x184, logs 352x262 (design px at 1080p), nothing cropped or overlapping. A new widget needs nothing, unless it has a scrolling region: add its selector to `ELASTIC` (`tests/test_webMinSize.py` lists the known ones). A control that only appears on hover and is drawn over the content (the volume bar, `OVERLAYS` in `ui.js`) is drawn absolutely and takes no room, so while measuring it reserves the strip it covers on its container's right (its own width + its distance from the edge + 8 design px of gap, all read from the live element): at the old minimum the bar sat 12 px into the repeat button's column (media 214 px wide); now the minimum is 240 px and the bar clears the repeat button by 14 px, with no padding added to the widget. The Spotify widget's seek row also steps left of the volume fader while the fader shows (`.media:hover .m-seek`), so the mute button never sits on the song's total time.

## Settings, lights and Claude fixes (web)
- **Presence status is spoken once per session, from the Presence tab only.** `monitor.status` makes the monitor SPEAK ("No device is paired..."), and the tab used to send it while the Settings window was built, so every open of Settings said it. Now `presenceTab` returns a `show()` hook that `settings.js` calls when the user clicks the tab, wrapped in `once()` (`presence-model.js`), so it asks at most once until the page reloads. The tab shows the state from the retained `jarvis/sys/presence` topic, no request needed. Tests: `tests/test_webPresenceStatus.py`.
- **Lights: the bulb disc is the colour button.** The separate swatch button on the right is gone; clicking the disc (which shows the light's state and colour) opens the colour popover, clicking it again closes it, and a light without colour support keeps a plain indicator. The popover's left edge lines up with the disc (`picker-spot.js`; it used to right-align to a button that was on the right). Tests: `tests/test_webPicker.py`.
- **Claude: the grid follows the window width again, so there is never a horizontal scrollbar** (`overflow-x: hidden` as a hard guarantee). This reverses the "never resizes" decision from earlier: that left the terminal at the bridge's width and scrolled sideways, and it was only needed because the Qt widget was also sizing the same terminal. With the desktop shell as the UI the Qt widget is off, so the web window is the single owner: `claude.resize` (debounced, only when the grid changed), columns from the window (floor 40, below the window's smallest width), rows floored at 40 so the input box never falls off a short grid. The emulator does not reflow, so lines drawn before a narrowing resize stay at their old width and are clipped on the right; new output fits. If the Qt dashboard's Claude widget is also open the two fight (see the to-do list).

## Window layout (web)
A window's saved layout (`localStorage` `jarvis.layout.v1`, per window id) is its position as fractions of the viewport and its size in design px (`web/js/layout-model.js`), and **it is the source of truth**: where a window is drawn is computed from it (`ui.js` `refit`), never from where the window happens to be. Found live: moving between the shell's overlay and dashboard sent every open window to 0,0, because the old `resize` listener clamped each window in place and in the overlay (a 200x400 page, windows `display: none`) every rectangle was 0x0 at 0,0. Now: `refit` skips the overlay, re-places every window from its saved layout on a viewport change and when the mode changes back (the monitor may differ), a window gets a saved layout the moment it opens (not only after its first drag), and nothing is saved from a window that is not drawn. Reproduced and verified in the render-only shell by opening a window at a saved spot and going overlay <-> dashboard twice (`JARVIS_SHELL_EVAL` prints the final rectangle). Tests: `tests/test_webLayout.py`. The layout lives in the shell's own browser profile (`data/shell_profile/`), so the layouts from a browser tab do not carry over.

## Dock pills (web)
Like the Qt `IconPill`: a round icon that opens on hover to show its label. **Timing**: an 80 ms hover delay (a pointer sweeping past opens nothing), then a 260 ms ease-out (`--open-delay` / `--open-ms` in `style.css`), the same numbers as Qt; it was 150 ms with no delay and felt abrupt. **No native hints**: the pills have no `title`, the label opening is the hint (accessibility keeps `aria-label`). **Marquee** (`web/js/pillmarquee.js`, a port of `MarqueeLabel`): the label opens to the width JS measured for its text (`--lw`), capped at 170 design px; a longer text (a long device name) is shown with an ellipsis, held still for 0.8 s after the hover starts, then scrolls left at 1 px per 40 ms and comes back in from the right edge until the pointer leaves. Pure parts tested in `tests/test_webPill.py`. **Layout**: the mic and speaker pills are a centred pair directly above the text bar (the mic opens to the left, the speaker to the right, so they never grow into each other), like Qt; the lyrics' centre line moved up from 205 to 240 design px to clear them (a wrapped dock row still pushes them to 271). Render-only hover check: `JARVIS_SHELL_HOVER=x,y` in the shell's test mode.

## Settings (web)
`web/js/settings.js` is built once from a small tab/row table and synced in place from `GET /api/settings` (polled every 3 s while open, so a voice command that flips silent mode shows up). A change is `POST /api/settings {key, value}`: `clWebUI.py` hands it to `src/utils/clWebSettings.py`, an **allow-list** (fixed keys, bools must be real booleans, choices checked) over `core.json` written with `update_json_atomic`; `start_on_login` goes to `clAutostart` instead. The page then dispatches the live action (silent mode, follow-ups, ecosystem mode, debug flags) like the Qt widget, and settings that need a restart (theme, STT model/mode, hardware) show "Save & Reboot Ecosystem" (`system.restart_all`). The POST is a write endpoint on localhost: it refuses a foreign `Origin` and anything but a JSON body (same rule as the WebSocket). Tests: `tests/test_clWebSettings.py`. To add a tab's settings, add the key to `clWebSettings.SETTINGS` and a row in `settings.js`. All Settings tabs are ported.

## Calendar drawer (web)
`web/js/calendar.js` (UI) + `web/js/calendar-model.js` (pure date logic, no DOM). Edge tab on the right (the chevron rides the drawer's edge), "U3" design from the Calendar Drawer Designs artifact: month title + year (click = year picker), prev/next, Today, DAY/WEEK/MONTH pill, Monday-first grid with up to 3 event bars per day (solid = local, hollow = Google), then the sheet: selected day, its events (a local one opens the edit dialog, a Google one is read-only with a GOOGLE tag), the next two busy days, and `+`. Width is the Qt rule in CSS (`--cal-w`: 400u from 1920 px wide, else 350u, never over 90% of the window). Data is the same as Qt: `jarvis/sys/calendar/status` (asked for with `calendar.read` when the page starts and when the drawer opens); save/edit publishes `jarvis/sys/calendar/create {event, time_str: "yyyy-MM-dd HH:mm", id?}` and delete is `calendar.delete`; the daemon (`clUtilities`) stays the only writer of `data/events/`. Below the agenda is the Qt drawer's carousel: a round icon dock (To-do with an open-task badge, Reminders, Media, Lights) over the stack, each page the same widget as its dock window (`def.build(host)`, built on first pick), then the now-playing pill (`jarvis/sys/media_status`, `spotify.control` prev/toggle). **The widget area's height is adjustable**: drag the bar above the dock (up = taller), arrow keys nudge it, double-click resets to 240 design px; saved in `localStorage` (`jarvis.calendar.stackH`, design px, so it follows the screen scale). The agenda above keeps at least 84 px and the stack's `flex-shrink` keeps a saved height inside a smaller window (verified with synthetic pointer events: drag, clamp both ways, reset, keys). **The calendar's size is adjustable too**: the sheet's grab handle at the top is a splitter; dragging it down makes the day cells taller (the calendar grows, the agenda and then the widget area give up space down to their minimums), up makes them shorter. The stored value is the cell shape `--cell-k` = height / width (1 = the square U3 look, 0.5 to 2.2; `aspect-ratio: 1 / var(--cell-k)`), `localStorage` `jarvis.calendar.cellK`; double-click resets, arrows nudge. `?open=calendar` opens it at start. Tests: `tests/test_webCalendarModel.py` runs the model under node (skipped without node); the DOM was checked by rendering month/week/day/year/dialog headlessly with a stubbed bridge.

## Portrait
The orb's loudest wave was `height / 4` (Qt and the first web port): 270 px at 1080 tall, 480 px on a 1920-tall portrait screen, and doubled on 4K because drawing multiplies by the unit again. The web orb now uses `min(W, H) / 4 / unit` design px, so a screen has the same wave size either way up. Further ideas if portrait still feels heavy: a 0.75 factor for portrait, a narrower wave span, a smaller bloom, fewer particles.

Lyrics and the wrapped dock: when the dock wraps (portrait / narrow) its rows stack above the bar, with the mic/speaker pills highest (about 152 u above it), so `fitDock` also puts `dock-compact` on `<body>` and the lyrics move up to 216 u (`.dock-compact #lyrics`); in landscape they stay at 150 u.

## Skins (web)
The skin is the Qt one, not a second palette. `clWebUI` serves `/style.css` through `clSkin.recolor_css` (the stylesheet is written in JARVIS orange, so the default skin is the file as it is and Ultron is a deterministic recolour: orange to crimson, cream to steel, dark brown to cold near-black), and `/api/config` reports the skin really in force (`JARVIS_THEME` overrides `settings.theme`, as in Qt), so the page never flashes the wrong palette. Colours built in JS (`web/js/skin.js`: the orb palette, the lyrics, the clock glow) go through a port of the same mapping (`ultronRgb`, `isAccent`, the 1.8 alpha boost); `tests/test_webSkin.py` runs both on a colour grid and checks the route. **Rules for new web code**: write colours in the JARVIS palette (CSS variables or literals in `style.css`) and they follow the skin; a colour in JS goes through `skinRgba`/`skinCss`; a colour that must not follow it (a bulb's real colour) is simply never passed through. Switch it from Settings > System > Assistant, then refresh. **The Ultron head replaces the orb: see below.**

**Tab strips wider than their window** (Settings, To-Do; `.tabs-pill`): the strip always scrolled sideways, but its bar is hidden and a mouse wheel only scrolls vertically, so tabs past the edge were unreachable. `enableTabScroll` (`web/js/ui.js`, logic in `web/js/tabstrip-model.js`, tests `tests/test_webTabStrip.py`) maps the vertical wheel to sideways scrolling (not at an end, so the page keeps the turn), fades the edge that has more tabs behind it (`.fade-l` / `.fade-r`) and keeps the selected tab in view whenever the strip is rebuilt or resized. Any new tab strip needs one `enableTabScroll(strip)` call.

**What survives a reload / restart / mode change** (`web/js/session-model.js`, tests `tests/test_webSession.py`): a mode switch never reloads the page (windows are hidden in the overlay, not closed), but a reload or a restart of the UI does. The open windows are saved to localStorage (`jarvis.open.v1`, on every `windows-changed`, only after the startup restore is done) and come back when the session continues: a page reload (sessionStorage `jarvis.seen`), or a shell started as a restart or crash recovery (`jarvisShell.reboot` = `JARVIS_REBOOT=1`). A cold start of the ecosystem opens only the pinned ones, as before; a plain browser tab always restores. Each window's own choice is saved too (`saveUiState`/`loadUiState`, key `jarvis.state.v1`): the Settings tab (`settings.tab`), the To-Do list (`todo.list`) and the Media drawer (`media.drawer`); the lyrics switch had its own key already. A new window with tabs or drawers should use the same helpers.

**Switching overlay <-> dashboard without a flash** (`shell/main.js` `setMode`, `web/js/shell.js`): the window is resized in the shell process and the page learns the mode a moment later, so the old layout used to be drawn in the new box for a few frames (the dashboard's windows squeezed into the overlay box). Now `setMode` first sends `shell:prepare`; the page adds `html.switching` (everything `visibility: hidden`, transparent), waits two frames and answers `shell:prepared`; only then is the window moved, the mode sent, and the veil lifted once the new layout has had three frames (+60 ms; a 1.5 s timer lifts it regardless, and the shell waits at most 250 ms for the answer). The first placement at start skips it. To see the order under the real Electron: run it with `JARVIS_SHELL_TEST=1 JARVIS_SHELL_MODE=fullscreen` and a `JARVIS_SHELL_EVAL` that records `<html>` class/data-mode changes before calling `window.jarvisShell.setMode('overlay')`: expect `switching` added, then `data-mode` flips, then `switching` removed.

**Opening windows by voice / text bar** (`web/js/ui-control-model.js`, handler in `web/js/main.js`, tests `tests/test_webUiControl.py`): `jarvis/sys/ui_control` `show_logs` (the `system.show_logs` intent) and `show_todo` open the Logs / To-Do window. `show_todo` is published by Utilities (`handle_todo_request`) whenever `jarvis/sys/todo/request` arrives **without `source: "ui"`**, i.e. from the `todo.list` intent ("show my todo list"); the To-Do window's own refresh sends `source: "ui"` (`todo.list` has that optional field in `actions.json`) so it does not re-open itself. In the dashboard the window opens there; from the overlay it floats (next paragraph). Qt ignores `show_todo`. Adding another voice-openable window: one entry in `SHOW_ACTIONS` plus whoever publishes the action.

**Pin / unpin = floating windows** (like the Qt widgets: `toggle_pin` in `src/clUI.py`; code in `shell/main.js` `openFloat`, `web/js/ui.js` `unpin`, `web/widget.html` + `web/js/widget-main.js`, geometry in `shell/geometry.js` `floatBounds`; tests `tests/test_shellGeometry.py` `TestFloatingWindows`, `tests/test_webUiControl.py`). A window is **pinned** (a part of the dashboard: hidden with it in the overlay; the dimmed `pin_off` icon) or **unpinned** (the bright `pin` icon): its own Electron window, always on top of other apps (`screen-saver` level like the overlay), draggable to any monitor, there also while the dashboard is just the overlay, which does not change. The old "pin = reopen after a restart" meaning is gone (every open window is restored anyway, see above). Unpinning keeps the window where it is (screen coordinates); its pin (now in its own window) pins it back into the dashboard (when only the overlay is up it opens with the dashboard). Each floating window is a renderer loading `widget.html?id=<window id>` (`widgetMode` in `ui.js`: the window fills the page, its title bar is `-webkit-app-region: drag`, the grip and the minimum size go to the shell by IPC, none of the dashboard's saved layouts is read or written; the unit comes from the monitor, not the small window). Cost: one extra Chromium renderer (~80-100 MB) per floating window. Floating windows and their bounds are saved in `data/shell_state.json` (`floating`) and come back on a restart or crash recovery (`JARVIS_REBOOT=1`), not on a cold start. **Hand-over without a gap or a shift** (tests `tests/test_webFloat.py`; verified under the real Electron with the `JARVIS_SHELL_FLOATS` hooks): *unpin*: the dashboard keeps its copy; the shell opens the floating window hidden at the exact screen position (`relative: true` rectangles are added to the dashboard window's bounds in main, not computed from `screenX`), the floating page says `floatReady` once its icons are in, its data connection is up and ~180 ms have passed (never later than 1.5 s; the shell waits 3 s at most), the shell shows it (no focus steal) and 60 ms later sends `shell:float-shown`, and only then the dashboard removes its copy. *Pin back*: the shell sends the floating window's bounds in dashboard coordinates (`shell:docked`), the dashboard opens its copy exactly there (`openWindow(def, at)`, saved as that window's layout), and after two frames answers `dockReady`, and only then is the floating window closed (1.5 s fallback); a window floating on another monitor is clamped into the dashboard like the Qt widgets. Window positions and sizes are whole pixels (`place`, `openWindow`), or a window and its floating twin would differ by a fraction of a pixel and blur. **Windows' own window animation:** DWM zooms a window in when it appears and fades it when it closes; on a floating window that read as a "little growth" at the swap. So a floating window is created with `setOpacity(0)` + `setIgnoreMouseEvents(true)` and shown at once (the animation runs unseen while its page loads); `showFloat` only sets the opacity to 1 and the mouse events back, and `closeFloat` drops the opacity before closing. Checked on the real OS window (GetLayeredWindowAttributes): alpha 0 and click-through while loading, 255 and clickable when shown. `JARVIS_SHELL_SHOW_FLOATS=1` lets a TEST run show its floating windows for that. Not carried over: the dashboard window's drop shadow (a floating window is clipped to its own rectangle).

**"Show the logs" / "show my todo list" from the overlay float the window** (the dashboard stays the overlay); in the dashboard they open it there; one that already floats is brought forward. Test hooks for the real Electron: `JARVIS_SHELL_FLOATS=1` (report the floating windows), `JARVIS_SHELL_FLOAT_EVAL=<js>` (run in each floating page first), `JARVIS_SHELL_AFTER2=<js>` (probe the dashboard after that).

**Zoom, part 1: the whole UI** (`web/js/zoom-model.js` pure + `web/js/zoom.js`, tests `tests/test_webZoom.py`). Zoom is a factor on the fluid unit, `U = base * Z` (`setUnit` in `main.js`; 60-200 %, 10 % steps, `--ug` holds the same value for a window's own zoom later), so everything written as `calc(N * var(--u))` is laid out again at the new size: crisp text, orb and clock scale, and (frames: see the revision below, they do NOT follow the zoom any more) `ui.js` listens to `jarvis-unit` (fired by `setUnit` after every change of the unit; windows also measure their minimum size again, `claude.js` re-measures its character cell and resends its grid). Input: `Ctrl +` / `Ctrl -` / `Ctrl 0` (capture phase, before a terminal sees them), `Ctrl`+`Alt`+wheel anywhere and `Ctrl`+wheel over empty space (a notch = one step, a trackpad adds up small turns); a badge says `Zoom 120 %` for a moment (double-click resets); Settings > System > Display has a slider and a reset. The state is `localStorage` `jarvis.zoom.v1` `{global, widgets}` (shared by the dashboard and every floating window, which follow through the `storage` event: their content scales). **The overlay is never zoomed** (fixed box, no input). Verified under the real Electron: 150 % gave a 381x437 window 572x656 with a 39 px title bar (26 x 1.5), Ctrl+0 and Ctrl+- restored and stepped it, the overlay stayed at 1 px, and a floating window went 380x440 to 570x660. A window that floats keeps its zoom state in the same object. **Zoom, part 2: a zoom per window** (same files; tests `TestPerWindowZoom` etc. in `tests/test_webZoom.py`). `Ctrl`+wheel over a window zooms that window alone (50-250 %): its **frame stays**, only the content scales. `ui.js` `applyZoom` gives the `.win` its own unit, `--u: calc(var(--ug) * Zw)` (`--ug` = the global unit, kept apart by `main.js`/`widget-main.js` `setUnit`, with a `1px` default in `:root` so the calc is never invalid), so the window zoom multiplies the global one (global 120 % x window 160 % = 192 %); `fitMin` measures in the window's unit (`unitOf`), so its minimum size rises with its zoom, while saved frames stay in design px of the *global* unit and a window zoom never reaches the layout. `Ctrl`+`Alt`+wheel over a window is the whole UI's zoom instead; in a floating window the whole page is the window, so its Ctrl+wheel is its own zoom. The badge names what changed (`To-Do List 160 %`, double-click resets that); Settings > System > Display has "Reset all" for the windows' zooms. State: `jarvis.zoom.v1` `widgets` (kept when a window floats or is pinned back; a change in one window of the UI reaches the others through `storage` -> `jarvis-widget-zoom`; `claude.js` re-measures its cell on it). Verified under the real Electron: Ctrl+wheel x5 -> 160 %, frame 381x437 unchanged, title bar 26 -> 41.6; then global 120 % -> frame 457x524, title bar 49.9 (26 x 1.2 x 1.6); Ctrl+Alt+wheel moved the global zoom; a floating window's minimum size grew 1.5x with its zoom while its OS window stayed 380x440. Not zoomed by a window zoom: popovers appended to `<body>` (the colour picker, menus), which use the global unit.

**Zoom, revision: the frames stay, only the content scales** (the first version made every frame follow the global zoom, so zooming out shrank all windows; the owner wanted them kept as they are). `main.js` / `widget-main.js` `setUnit` now set `--ub`, the unit **without** the zoom, next to `--u` (with it); `ui.js` `baseUnit()` (`--ub`) is what a window's frame is made of (its size at open, its position, `persist` / `refit` and so its saved layout), `unit()` (`--u`) and `unitOf(el)` are what its content and its measured minimum size use. So a global zoom leaves every frame where and as big as it is, the title bar gets thinner and the text smaller (zoom out), and a window only **grows when its content, zoomed in, no longer fits** its size (its minimum, `applyMin`), going back to its frame when zoomed out again. A floating window's OS window no longer follows the global zoom either (it grows by the same rule through `minSelf`). Verified under the real Electron with the Music and Lights windows open: at 70 % both frames stayed 430x259 and 380x420 at 16,48 and 460,48 while the title bar went 26 -> 18.2 px and the text 12 -> 8.4 px; at 130 % Lights stayed 380x420 and Music grew only in height (259 -> 336) to fit; back at 100 % it was 430x259 again. Layouts saved while an earlier build was zoomed were stored in the zoomed unit: reset the zoom to 100 % and move or resize such a window once to save it again.

## Lyrics layout (web)
`web/js/lyrics.js`: **a line is wrapped once, at the style it will have as the current (big) line, and shown with those line breaks (`white-space: pre`) in every row**, so growing or shrinking it never re-wraps (the earlier version wrapped at each row's own size, so lines reflowed as they animated). Wrapping measures with a canvas at the big font and the real width (`min(700u, window - 32u)`), breaks over-long words by character, and caps a line at 4 lines with an ellipsis; it is redone on resize and when the font loads. **Rows are as tall as their lines need and nothing is clipped**: `#lyrics` is a zero-height centre line (205u above the bottom, 271u when the dock wraps), the current line is centred on it, the next grows upward and the previous downward. The revolver animates the three moving lines as one stacked column anchored by the sinking line, so they cannot overlap and the first/last frames are exactly the resting layouts (measured: no overlap beyond the first, invisible frame at 0.6x, 1x and 2x scale). **Settings (Settings > System > Display > Lyrics, client-side in localStorage `jarvis.lyrics.v1` like the zoom, so no core.json key):** upcoming lines (0-5, default 1), previous lines (0-5, default 1) and a font size (80-160 %, default 100 %) that scales the big and the small lines together (`--ly-s` on `#lyrics`, and in the wrap measurement and the revolver). `lyrics-model.js` holds the clamps and `bottomShift` (pure, `tests/test_webLyrics.py` under node); `lyrics-settings.js` the state and the `jarvis-lyrics-settings` event (also fired by the `storage` event, so the floating Settings window reaches the dashboard). **Rows shrink with their distance from the current line** (`rowPx` in `lyrics-model.js`: 14 px next to it, then x0.88 per place, never under 8 px; the revolver interpolates each row between its old and new distance), each row is also 20 % fainter than the one before (floor 35 %, `opacityAt`), and **the gap above a row is 60 % of its own font size** (`gapAt`: 8.4 u next to the current line, less further out; it was a fixed 4 u). **The column lives in the gap between the visualizer and the pills** (`plan` in `lyrics-model.js`, applied by `applyPlan` in `lyrics.js` on show, resize, zoom/`jarvis-unit`, skin change and settings change): the highest pill or the command bar is measured from the DOM (`#dock .pill, #dock .text-bar`), so the wrapped dock is handled without a CSS number; the visualizer's lowest point is 105 u under the screen centre (rings), 160 u for Ultron (the head). The column's bottom edge stays at its default place (205 u above the screen bottom, 236 u with the wrapped dock) while it fits above it, so extra lines only stretch the top; if it does not fit it is lowered towards the pills but **never closer than 28 u to the highest pill**; if the whole gap is still too small it gives way in this order: the font shrinks to 75 % (`fit`), the outermost rows are dropped until one is left on each side (`shown`, so the current line keeps some context), the font shrinks further (to 45 %), and only then are the last rows dropped. If nothing fits it still keeps the pill padding and reaches up into the visualizer. Fitting uses a nominal column (a two-line current line, one-line rows); lines that wrap to more rows than that raise the whole column (`lift` in `metrics`) instead of reaching down into the pills. The revolver is generalised to N rows: the sinking line anchors a column, the next rows stack above it (the brand-new line grows in last) and the previous rows below it (the oldest fades out); with 0 upcoming lines the rising line fades in, with 0 previous lines the sinking line fades out. Changing a setting mid-revolver cancels it and rebuilds the rows. Not ported to the Qt `LyricsDisplay`. Checked headlessly (Electron with `offscreen: true` - a hidden window never runs `requestAnimationFrame`, so an earlier check that only looked at frame 0 proved nothing; stubbed bridge, real `style.css` and dock markup, wrapped and normal dock): with a fake pill row, long wrapping lines and 1/1 to 5/5 at 80-160 %, the lowest line is always at least 28 px above the pills, at rest the rows never overlap and the animation ends on the resting layout; during the revolver the only overlap is the brand-new line sliding up (12 u, fading in); the DOM part has no automated test.

## Live Logs (web)
`web/js/logs.js` + `GET /api/log?pos=<offset>&raw=0|1` and `POST /api/log/terminal {raw}` in `clWebUI.py`, on the same Qt-free `utils/clLogTail.py` as the Qt widget and the terminal. The server keeps no state: the page sends the byte offset it has reached and gets the whole lines written since (the first call has no offset and is the tail: 256 KB condensed, 96 KB raw, never the whole multi-MB file), with `restarted: true` when a new run rewrote the log. **Condensed** (default) drops heartbeat topics and protocol chatter, cuts long lines and redacts Bearer tokens in both modes; **Open terminal** spawns `clLogTail.py` in its own console in the view's mode (same-origin + JSON-body guard, as it starts a process; replies `{ok: false}` and the button says "No terminal found" when there is none). The page keeps the last 3000 lines and its 500 ms poll stops while the window is closed or the tab hidden. **It is drawn as a terminal, with no input into it**: a dark screen headed `$ tail -f logs/latest_run.log` (`# raw` in raw mode), a dim timestamp, a stable colour per `[TAG]` (hash of the name into 6 terminal colours), MQTT topics in cyan, error lines red and warning lines amber, a blinking block cursor after the last line (static with `prefers-reduced-motion`), and a `↓ follow` button when you scroll away from the bottom (it sticks to the bottom only while you are there). **Lines wrap at the screen's edge like a terminal** (`white-space: pre-wrap; word-break: break-all`, mid-word if it has to, no horizontal scroll, so resizing the window re-wraps everything). **The bar at the bottom is a filter, not a command line** (`web/js/logfilter.js`, pure and tested under node): every word must be in the line (case-insensitive), `-word` hides lines containing it, matches are highlighted, a `shown / kept` counter and `×` appear, Esc clears; it applies to the kept 3000 lines and to new ones. ANSI colour codes are stripped by `clLogTail.condense` (the log has none), so the colours come from the tag, not from escape codes. Tests: `tests/test_webLog.py`.

## Scrollbars (web)
One global style in `style.css` for every scrolling area (no per-widget rules): no track, no arrows, a slim rounded thumb floating off the edge (a transparent border + `background-clip: padding-box` makes the thumb narrower than its gutter, so it can thicken on hover), faint at rest, brighter while the area under the pointer is hovered, thick and bright under the pointer, accent-bright while dragged. Sizes follow `--u` with pixel floors (`--sb-gutter`, `--sb-inset`). Chromium/WebKit use the `::-webkit-scrollbar` pseudo-elements; **do not also set `scrollbar-width`/`scrollbar-color` on the same elements: Chromium 121+ then ignores the pseudo-elements**. Firefox gets `scrollbar-width: thin` + `scrollbar-color` through `@supports not selector(::-webkit-scrollbar)`. The tab-pill rows hide theirs (they scroll sideways without a bar). The colours are the accent's, so the skin recolours them. Pure CSS: a JS overlay would need a positioned wrapper around every scroll container, and the layouts here are too varied for that to be safe.

Scrollbar position: a scrolling area inside a padded panel is pulled out to the panel's edge with a negative margin and keeps the padding inside (`.mod-list`, `.rem-grid`, `.set-pages` -20u like `.mod`'s padding; `.cal-events` and `.cal-stack` -22u like the calendar sheet), so the bar sits flush at the window's right edge and the content does not move. A new scrolling area inside a padded panel needs the same pair of lines, with the parent's padding.

## Claude window (web)
`web/js/claude.js` + `web/js/claude-model.js` (pure, tested under node: `tests/test_webClaude.py`). **No xterm.js**: `clClaudeBridge.py` already emulates the terminal (tmux / ConPTY+pyte) and publishes full snapshots on `jarvis/claude/screen` (`{text, mode, idle?, cursor?: [col,row], ansi?}`), so the page just draws rows and forwards keys, like the Qt widget outside Claude's input box: a **pure mirror**, no prediction, nothing vendored. Keys go as a terminal sends them: printable text and paste `claude.keys`, Enter/arrows/Home/End/Delete/PageUp/PageDown/Esc/Shift+Tab/Ctrl+arrows `claude.control_key`, Ctrl+letters their control byte (Ctrl+Z is never sent: it suspends the CLI), Ctrl+Backspace is Ctrl+W, Ctrl+C copies when text is selected and otherwise interrupts. Typing `/terminal` or `/claude` and pressing Enter erases the typed text and sends it as `claude.ask` (the bridge switches backend); the header button does the same. **(Superseded, see "never resizes" below: the window no longer resizes the grid.) Resizing the window resizes the real terminal grid** (`claude.resize`, debounced 300 ms, cols/rows from the measured cell size, min 20x5). **Colours** are the Qt widget's orange-only scheme made skin-aware: an ANSI colour is reduced to its brightness (same maths, a parity test against `clClaudeWidget._brightness`) and drawn as a `color-mix` between a dark accent and `var(--accent)`; reverse video is a solid accent block; at an idle shell prompt what is drawn after the cursor (the shell's suggestion) is dropped. **Not ported yet**: the local line editing Qt does inside Claude's framed `❯` box (text, cursor and Ctrl+A/E/U/K/W handled locally and written on Enter) and the slash-command popup; here every key round-trips over MQTT, so typing there is a little laggier. Opening the window sends a `claude.resize` for its size, which also resizes the live session.

**Claude window look (first pass).** The old header strip is gone: the title bar carries a state chip after the title ("session" / "shell", "working" with a pulsing dot while Claude shows "esc to interrupt" or a program runs in the shell: `isBusy`) and a `>_` button before the pin that switches Claude/shell (`ui.js` now hands a window's `build` its `head`, `title` and `pin`). The screen uses the skin's `--text` for default text, a dark radial gradient and a faint accent scanline overlay. Focus is visible: a glowing solid cursor and border when focused, a hollow cursor, dimmed rows and a "click to type" hint when not. The font is at least 12 px (`max(12px, ...)`, ligatures off) and symbols outside the monospace font (`● ❯ ✻ ⎿`, box drawing, arrows: U+2190-2BFF) are each pinned to one cell (`cellRuns`, `.cl-sym`) so a fallback glyph cannot shift the columns after it. Not done yet: styling prompt/reply/status rows by their first glyph, zoom (Ctrl+scroll), skin check on Ultron.

**Claude window: never a short terminal grid.** Found live: with a ~25-row grid (a small window) the input box was missing and the cursor sat mid-screen, because Claude redraws a frame as tall as the whole conversation and the bottom of it (the box) falls off a short pyte screen; at 40 rows it is back. The window therefore always asks the bridge for at least 40 rows (`MIN_ROWS` in `claude.js`, `gridFor(..., minRows)`); a window shorter than that scrolls, pinned to the bottom (the input) until you scroll up, and typing re-pins. Columns still follow the width. A shrink does not make the TUI redraw by itself, so lines drawn for a wider grid stay cut until the next output. This is the bridge's pyte limitation and applies to the Qt widget too (its tall portrait window just hides it).

**Claude window: local line editing (the "slow" fix).** The first web version was a pure mirror: every key went browser -> WebSocket -> MQTT -> bridge -> terminal -> (150 ms debounce) -> snapshot -> back, so typing lagged (the Qt widget never did, it edits the line locally). `web/js/claude-line.js` (`LocalLine`, pure, clock injected, `tests/test_webClaudeLine.py`) now ports the Qt local editing: while Claude's framed `❯` box or an idle readline shell prompt is showing, text, cursor, selection, Home/End, word moves, Ctrl+A/E/U/K/W/X/C, paste and Backspace/Delete all act on a local buffer and send **nothing**; Enter sends `Ctrl+E Ctrl+U + text` and Enter as one message; Tab, Up/Down and other Ctrl+letters sync first and then re-adopt the CLI's own line; Esc and Shift+Tab go straight through. Snapshots never overwrite unsent edits, and for 0.8 s after a sync/Enter the stale line is not re-adopted. A typed `/terminal` or `/claude` is sent as text, never typed into the CLI. The IDE-selection chip (`[⧉ In file]`) is not part of the line. Only the edited row is redrawn on a keystroke (the full screen only on a snapshot), and `claude.resize` is only sent when the grid actually changed. Menus, programs running in the shell and cmd.exe stay a pure mirror. **Grid floor 120x40**: shrinking the grid leaves the bridge's pyte screen and Claude's incremental redraw out of step (stale lines, the input box gone: found live after repeated resizes), so a window narrower or shorter than that scrolls instead of resizing the session; a larger one still grows it. Not ported yet: the slash-command popup, zoom.

**Claude window: never resizes the terminal grid.** Found live: the Qt dashboard's Claude widget sizes the real grid to itself (~62x21, by design) and the web window sized it to 120x40, so with both open they overwrote each other every few seconds and each shrink left the bridge's screen stuck (stale lines, no input box; keys were logged by the bridge but the screen never changed, which looked like lag). The web window now only draws the grid the bridge reports (scrolling when it is smaller or larger) and sends no `claude.resize`; `gridFor` stays in `claude-model.js` for when a single-owner sizing scheme exists. A stuck screen is cleared by restarting the Claude Bridge module.
