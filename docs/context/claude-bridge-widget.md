# Claude voice bridge — dashboard widget, /terminal mode, resize

Read when working on `src/ui/clClaudeWidget.py`, the `/terminal` ⇄ `/claude` mode switch, `clPlainTerminalBridge.py`/`clWinTerminalBridge.py`, or terminal resizing. Backends: `docs/context/claude-bridge-core.md`.

- **"/terminal" ⇄ "/claude": a second backend, same widget.** `ClaudeBridgeService` runs two independent backends side by side — `self.bridge` (the claude session) and `self.terminal_bridge` (a plain shell, no onboarding auto-answers/sign-in detection/stall recovery, none of which apply to a bare shell prompt) — with `self.mode` deciding which one's screen is published to `jarvis/claude/screen` and which receives typed input. Typing `/terminal` or `/claude` into the widget is intercepted by `run()`'s message loop as a local mode switch, never forwarded as literal text; neither backend is ever stopped on a switch, so toggling back is instant and loses no state, and each backend's `refresh_screen()` forces an on-demand capture so the widget shows the right content immediately on switch instead of waiting for new output. `src/utils/clPlainTerminalBridge.py` (`PlainTerminalBridge`) is the Linux backend: tmux running the user's `$SHELL`, same `pipe-pane`-into-a-FIFO pattern as `ClaudeTmuxBridge`. `src/utils/clWinTerminalBridge.py` (`WinTerminalBridge`) is the Windows backend: ConPTY via `pywinpty` running `%COMSPEC%` (falls back to `cmd.exe`), rendered through `pyte` — the same ConPTY+pyte pairing `ClaudePtyBridge` already uses for the claude session, just without any of `ClaudeSessionBase`'s onboarding/stall logic, mirroring `PlainTerminalBridge`'s relationship to `ClaudeTmuxBridge` on Linux. Both backends expose the same `send_control_key(token)` entry point the widget's keyboard handling (Esc/Shift+Tab/arrows, see below) dispatches through; on a plain shell, `"ESCAPE"` maps to Ctrl-C (interrupting a running command) rather than an actual Escape keypress, since there's no TUI to escape out of. `clClaudeBridge.py`'s `_terminal_backend_class()` picks the backend by `CURRENT_OS`, same split as `_backend_class()`.
- **The widget has no separate input box — you type directly onto the screen mirror, like a real terminal.** `ClaudeTerminalView` (`src/ui/clClaudeWidget.py`, a `ZoomTextEdit` subclass) is `setReadOnly(True)` at the Qt level and funnels every keypress through its own `keyPressEvent`. Anywhere the local line editor below doesn't apply (a program running in the shell, a Claude menu, the Windows `cmd.exe` terminal) it is a **pure mirror**: no prediction at all — each key is forwarded as a terminal would send it (printable text/paste via `claude.keys` → `send_raw_keys`, Enter/arrows/Home/End/Delete/PageUp/PageDown/Esc/Shift+Tab/Ctrl+arrows via `claude.control_key`, other Ctrl+letters as their control byte, Ctrl+Backspace as Ctrl+W) and the screen shows only what the backend's next snapshot says. The only local state is `_shadow`, a copy of what was typed since the last Enter, used solely to recognise `/claude` / `/terminal` typed into a shell. The slash-command `QCompleter` only exists inside Claude's input box.
- **No suggestions:** the terminal never shows a shell autosuggestion — at an idle prompt everything drawn beyond the cursor is dropped (`_suggestion_cut`), in local editing and in the pure mirror alike.
- **Colours:** `/terminal` captures with `tmux capture-pane -e` (no `-J`, so wrapped lines look like the pane) and the bridge publishes the plain text plus an `ansi` field on `jarvis/claude/screen`; the widget renders SGR attributes (`ansi_spans`) so e.g. zsh-autosuggestions' grey suggestion is distinguishable from typed text. **The terminal keeps the dashboard's orange-only scheme:** every ANSI colour is reduced to its brightness (`_brightness`: luminance for greys, strongest channel for saturated colours) and drawn on an orange ramp from dim orange to the theme's `#ffaa00` (`orange_shade`); coloured backgrounds become translucent orange tints, reverse video is a solid orange block with dark text, and bold/italic/underline/dim are kept. The Claude session's screen stays plain text (its prompt/busy detection parses it), and the Windows `WinTerminalBridge` is still plain (pyte's attributes aren't converted yet). The cursor comes from the backend (`cursor` field) and is drawn as a blinking block.
- **Resizing the widget really resizes the terminal grid**, not just a display clamp on a fixed 120x40 session. `ClaudeTerminalView.resizeEvent()`/`zoomIn()`/`zoomOut()` debounce (300ms) into a `claude.resize` dispatch (`cols`/`rows` computed from `viewport()` pixels ÷ `fontMetrics()` character-cell size, min 20x5). `ClaudeBridgeService._resize()` applies it to both backends at once (not just the active one, so switching `/claude`⇄`/terminal` never finds the other stale) and remembers it so a backend started later comes up at the right size. `ClaudePtyBridge`/`WinTerminalBridge` resize both the real ConPTY (`PtyProcess.setwinsize(rows, cols)`) and the local `pyte.Screen`; `ClaudeTmuxBridge`/`PlainTerminalBridge` run `tmux resize-window -x/-y` (works directly since these sessions are always detached, never fighting an attached client's own size). The debug log viewer (`clLogWidget.py`) needs none of this — it's not a PTY, and already reflows on resize via ordinary Qt layout.
- The widget's input isn't mirrored into tmux live: text only reaches the terminal once dispatched over MQTT, so a static line sitting in the raw tmux pane is stale terminal state, not the user typing.
- **While Claude's framed `❯` input box — or a readline-style shell prompt in `/terminal` — is showing, the widget edits the line 100% locally** (`ClaudeTerminalView(local_line_editing=True)`): text, cursor, Home/End/Left/Right/Delete, Ctrl+A/E/U/K/W and paste all act on a local buffer and send nothing. Enter overwrites the CLI's line (`Ctrl+E Ctrl+U` + the local text, via `claude.keys`) and then presses Enter, so the CLI can never disagree with what was on screen. Keys that need the CLI's own copy of the line (Tab, Up/Down, other Ctrl+letters) sync first and then re-adopt whatever line the CLI ends up with; Esc/Shift+Tab/Ctrl+C go straight through. Snapshots only replace the buffer when there are no unsent local edits (never within `HOLD_S` of a sync/Enter). Shells and menus (no framed prompt) keep the older live-forward path with op-based prediction.
- **Shell prompt detection is index-based, not pattern-based.** The bridge tags every screen with `mode` (`claude`, `terminal`, or `terminal-basic` for the Windows `cmd.exe` backend, `READLINE_EDITING = False`) and, in terminal mode, `idle` — whether the pane's foreground process is a shell (`tmux_at_shell`: `#{pane_current_command}` in a known shell set), so a running program, `sudo`'s password prompt or `vim` are never treated as a prompt. While idle, the editable text starts at the **cursor column of a fresh prompt** (`_shell_start`, i.e. the prompt's own length, whatever characters it contains — `C: > `, `PS>`, `└─$ `); it is re-measured on every snapshot until the user touches the line, then fixed, reset on Enter, and re-measured once the post-Enter hold (`HOLD_S`, re-checked by `_hold_timer`) is over. Editing (Backspace, Ctrl+W/U, Home) can never go before that index; the line's text is what lies between it and the cursor (anything after the cursor is the shell's grey suggestion). A cursor at column 0 means the prompt isn't drawn yet, so nothing is editable locally. Ctrl+A/Ctrl+E are beginning/end of line in a shell (select-all only in Claude's box), the slash popup never shows in a shell, and the prompt keeps its colours while the line is edited locally.
