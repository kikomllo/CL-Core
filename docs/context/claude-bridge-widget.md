# Claude voice bridge — dashboard widget, /terminal mode, resize

Read when working on `src/ui/clClaudeWidget.py`, the `/terminal` ⇄ `/claude` mode switch, `clPlainTerminalBridge.py`/`clWinTerminalBridge.py`, or terminal resizing. Backends: `docs/context/claude-bridge-core.md`.

- **"/terminal" ⇄ "/claude": a second backend, same widget.** `ClaudeBridgeService` runs two independent backends side by side — `self.bridge` (the claude session) and `self.terminal_bridge` (a plain shell, no onboarding auto-answers/sign-in detection/stall recovery, none of which apply to a bare shell prompt) — with `self.mode` deciding which one's screen is published to `jarvis/claude/screen` and which receives typed input. Typing `/terminal` or `/claude` into the widget is intercepted by `run()`'s message loop as a local mode switch, never forwarded as literal text; neither backend is ever stopped on a switch, so toggling back is instant and loses no state, and each backend's `refresh_screen()` forces an on-demand capture so the widget shows the right content immediately on switch instead of waiting for new output. `src/utils/clPlainTerminalBridge.py` (`PlainTerminalBridge`) is the Linux backend: tmux running the user's `$SHELL`, same `pipe-pane`-into-a-FIFO pattern as `ClaudeTmuxBridge`. `src/utils/clWinTerminalBridge.py` (`WinTerminalBridge`) is the Windows backend: ConPTY via `pywinpty` running `%COMSPEC%` (falls back to `cmd.exe`), rendered through `pyte` — the same ConPTY+pyte pairing `ClaudePtyBridge` already uses for the claude session, just without any of `ClaudeSessionBase`'s onboarding/stall logic, mirroring `PlainTerminalBridge`'s relationship to `ClaudeTmuxBridge` on Linux. Both backends expose the same `send_control_key(token)` entry point the widget's keyboard handling (Esc/Shift+Tab/arrows, see below) dispatches through; on a plain shell, `"ESCAPE"` maps to Ctrl-C (interrupting a running command) rather than an actual Escape keypress, since there's no TUI to escape out of. `clClaudeBridge.py`'s `_terminal_backend_class()` picks the backend by `CURRENT_OS`, same split as `_backend_class()`.
- **The widget has no separate input box — you type directly onto the screen mirror, like a real terminal.** `ClaudeTerminalView` (`src/ui/clClaudeWidget.py`, a `ZoomTextEdit` subclass) is `setReadOnly(True)` at the Qt level so QTextEdit's own typing/paste never mutates it directly, and instead funnels every keypress through its own `keyPressEvent`. Plain characters, Backspace, and paste (Ctrl+V) are echoed locally — appended to/trimmed from a `_pending` string rendered after the last known server screen — *and* forwarded live via a `claude.keys` action (`config/actions.json`, same `jarvis/claude/question` topic as `ask`/`control_key`, routed to `send_keys()` on whichever backend is active); this local echo is what makes typing feel instant despite the MQTT round trip, and `_pending` is simply dropped the moment a new full-snapshot screen arrives, since everything typed by then has already been sent (each keystroke dispatches synchronously on press). Arrows/Escape/Shift-Tab/Enter get no local prediction — forwarded as before via `control_key`, since their real effect (CLI history, its own completion, an interrupt) depends on server-side state this view can't guess. The slash-command `QCompleter` survives having no `QLineEdit` to anchor to: `setWidget(self)` attaches it to `ClaudeTerminalView` directly (the standard Qt "Custom Completer" pattern), filtered off `_pending`, with Enter/Escape/Tab/Backtab explicitly deferred to the completer's own accept/dismiss handling while its popup is open.
- **Resizing the widget really resizes the terminal grid**, not just a display clamp on a fixed 120x40 session. `ClaudeTerminalView.resizeEvent()`/`zoomIn()`/`zoomOut()` debounce (300ms) into a `claude.resize` dispatch (`cols`/`rows` computed from `viewport()` pixels ÷ `fontMetrics()` character-cell size, min 20x5). `ClaudeBridgeService._resize()` applies it to both backends at once (not just the active one, so switching `/claude`⇄`/terminal` never finds the other stale) and remembers it so a backend started later comes up at the right size. `ClaudePtyBridge`/`WinTerminalBridge` resize both the real ConPTY (`PtyProcess.setwinsize(rows, cols)`) and the local `pyte.Screen`; `ClaudeTmuxBridge`/`PlainTerminalBridge` run `tmux resize-window -x/-y` (works directly since these sessions are always detached, never fighting an attached client's own size). The debug log viewer (`clLogWidget.py`) needs none of this — it's not a PTY, and already reflows on resize via ordinary Qt layout.
- The widget's input isn't mirrored into tmux live: text only reaches the terminal once dispatched over MQTT, so a static line sitting in the raw tmux pane is stale terminal state, not the user typing.
