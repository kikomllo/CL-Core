# Cross-platform (Linux/Windows) behavior

Read when touching OS-specific code: `clTerminal.py`, `clSpotify.py`, `clUtilities.py`, `clKeybinds.py`, `clNetworkUtils.py`, `boot.py`, `clHealth.py`, `clReminderTrigger.py`.

- **Cross-platform parity**: this is a dual-OS codebase (Linux and Windows dev machines both run the full ecosystem), so OS-specific actions in `clTerminal.py` branch on `CURRENT_OS` rather than assuming Linux. Volume (`pycaw`/Core Audio on Windows vs. `wpctl`/`pactl`/`amixer` on Linux), media control (synthetic `VK_MEDIA_*` key events on Windows vs. `playerctl` on Linux — Windows has no OS-level play/pause split, only a toggle), and eco/DPMS mode (`ctypes` `SC_MONITORPOWER` + a synthetic mouse-nudge to wake on Windows vs. `xset dpms` on Linux) all have both branches implemented. `clReminderTrigger.py`'s desktop notification (a hidden PowerShell `System.Windows.Forms.NotifyIcon` balloon on Windows vs. `notify-send` on Linux) and volume read (`pycaw` vs. `amixer`) follow the same pattern. `pycaw`/`comtypes`/`winsdk` in `requirements.txt` are marked `sys_platform == 'win32'`-only. `clTerminal.py`'s `poll_media_status` background task publishes free, local "now playing" state to `jarvis/sys/os_media_status` on both OSes — `playerctl` (MPRIS) on Linux, SMTC (`winsdk`'s `GlobalSystemMediaTransportControlsSessionManager`) on Windows — whichever app the OS considers current, not necessarily Spotify. `poll_spotify_local_status` runs alongside it, filtering that same free/local source down to Spotify specifically (an MPRIS player named `spotify` on Linux; the SMTC session whose app user model ID contains "spotify" on Windows, found by scanning every session rather than trusting whichever one the OS calls "current") and publishing to `jarvis/sys/spotify_local_status`. `clSpotify.py`'s `status(lightweight=True)` prefers that free local reading over a real API call whenever it's fresh and reports `found: true`, falling back to the Spotify Web API otherwise (including whenever playback is happening on a different Spotify Connect device, which the local OS session can't see) — this is what keeps the ecosystem's most frequent Spotify status polling from burning API quota. Volume has no local-OS equivalent at all (SMTC has no percentage-based volume property, and the OS per-app mixer level isn't the same number as Spotify Connect's own device volume), so it always comes from `last_known_normal_volume` in this fast path, kept accurate by `clSpotify.py`'s own volume/duck actions rather than by polling. `clSpotify.py` reserves real Spotify Web API calls for playback commands other than the `toggle`/`next`/`prev` buttons (see "Spotify buttons without the Web API" below) and for reading volume — and it has real rate limits, see its `_check_rate_limit`.
- **Media change listeners** (`src/clTerminal.py`'s `watch_media_events`): the 10s timeout in `poll_media_status`/`poll_spotify_local_status` is now only a heartbeat. The real wake-up is `manager.media_trigger`, set (debounced 150 ms) by OS events — media keys, Spotify's own buttons, a track change, a player opening/closing — so the dashboard updates in ~250 ms. Windows: `SmtcEventWatcher` subscribes to the SMTC manager's `current_session_changed`/`sessions_changed` and each session's `media_properties_changed`/`playback_info_changed`, and re-subscribes sessions on `sessions_changed`. `timeline_properties_changed` fires every ~4.5s while playing for position drift, so it only pokes when the position *jumps* (`_on_timeline_changed`) — a seek, from our `seek` action or inside Spotify, fires nothing else. Linux: two `playerctl --all-players --follow` subprocesses (`status`, `metadata`). Every SMTC read shares one cached manager (`_get_smtc_manager`) instead of a `request_async()` per poll; the poll loops drop it on error and the watcher re-subscribes within 30s (Now Playing service restarts). `poll_spotify_local_status` still publishes every wake (the heartbeat is `clSpotify.py`'s freshness signal), but `SpotifyManager._local_status_changed` only lets it through to the UI's `media_status` when a visible field changed or the position jumped >1.5s off the interpolated course (a seek) — a quiet heartbeat updates the cached status and nothing else.
- **Spotify buttons without the Web API** (`src/utils/clLocalMedia.py`, used by `SpotifyManager.execute_command` for `toggle`/`next`/`prev`): Windows sends `WM_APPCOMMAND` straight to Spotify's main window (`Chrome_WidgetWin_1` of `Spotify.exe`; the hidden `Chrome_WidgetWin_0` windows ignore it) — targets the Spotify process, not whichever app owns global media-key focus — and falls back to Spotify's SMTC session when it has no main window (closed to tray). Linux uses D-Bus MPRIS on `org.mpris.MediaPlayer2.spotify`. If there's no local client at all, it falls back to the old Web API path. After a local press `last_command_local` is set and the MQTT listener skips its API status refresh (the listeners above push the change). Tests must never press real buttons: `tests/test_clSpotify.py` autouse-patches `send_spotify_command`. `play`/`pause`/voice-by-name still go through the API.
- **Shuffle / repeat / seek / queue** (`clLocalMedia.py`, `clQueueTracker.py`, `SpotifyManager`): `shuffle` (`enabled`), `repeat` (`mode` = off|track|context, the API's names) and `seek` (`position_ms`) go through `_local_first` — SMTC on Windows (`try_change_*_async`, seek in 100 ns ticks), `playerctl --player=spotify` on Linux — and a local call only counts as delivered once the session's own state shows it (`try_*` just means "accepted"); otherwise the Web API is used. `_local_first` has a per-kind circuit breaker (3 failures → API-only for 60s). Read state is free: `media_status` carries `shuffle`, `repeat`, `can_seek/next/prev` from the local session. The queue is API-only: `queue`/`queue_refresh` fetch it once (`refresh_queue`), then `QueueTracker` follows playback from the local session (title is the key; duration only breaks ties because the local duration can lag a track change) and publishes the retained `jarvis/sys/spotify_queue`. It refetches (one request) only when playback leaves the queue, ≤2 tracks remain (the API caps at ~19), or shuffle changes; nothing is tracked until a queue was first requested. New actions have no voice intents yet (adding them means retraining the SLM, see `training/CLAUDE.md`). Not verified live: actually toggling shuffle (it reorders the user's queue).
- **Process-sweep fallback**: `boot.py`'s single-instance restart sweep and `clHealth.py`'s Native UI status check both use `wmic` to find/kill processes by command line on Windows, with a `Get-CimInstance`-based PowerShell fallback for machines where `wmic` (deprecated by Microsoft) has been removed.
- **Alarm/reminder scheduling** (`src/clUtilities.py`'s `schedule_systemd_timer`): Linux uses `systemd-run --user --on-calendar=`, a real wall-clock trigger that survives DST shifts and system sleep. The Windows equivalent, `_schedule_windows_task`, builds a Task Scheduler XML task (`WakeToRun`/`StartWhenAvailable` enabled) instead of the old `time.sleep()`-in-a-detached-process approach, which drifted across DST and simply didn't fire if the machine was asleep at the target time. Cancellation on both platforms goes through `cancel_scheduled_timer` (`schtasks /Delete` vs. `systemctl --user stop`/`reset-failed`) rather than assuming `systemctl` exists.
- **WiFi SSID detection** (`src/utils/clNetworkUtils.py`'s `get_current_wifi_ssid`, consumed by `clControl.py` to pick a per-network light profile out of `config/devices.json`'s `networks` map): Linux uses `iwgetid`/`nmcli`; Windows uses `netsh wlan show interfaces` to read the literal broadcast SSID — not `Get-NetConnectionProfile`'s connection *profile name*, which Windows seeds from the SSID but a user can rename independently, and which fails outright on non-English Windows builds where the default adapter alias isn't "Wi-Fi".
- **Push-to-talk key resolution** (`src/clKeybinds.py`): evdev (Linux) resolves any `KEY_*` name generically via `getattr(ecodes, ...)`; pynput (the only backend Windows ever runs) has no equivalent, so `PTT_KEY_MAP`/`is_ptt_key` explicitly map the realistic set of single-key PTT candidates — Ctrl/Shift/Alt variants, Caps Lock, Space, F13–F24 — to pynput `Key` members. Hotkey dedup is state-based only on both backends (evdev's `active_hardware_actions`, pynput's `active_actions`) with no artificial minimum re-trigger interval, so a full release-then-repress fires immediately on both.
- **Spotify wakeup/launch** (`src/clSpotify.py`): `_wake_up_spotify` escalates in stages when nothing is playing. First it targets an already-running client directly — D-Bus's `org.mpris.MediaPlayer2.spotify` name on Linux, or `_wake_up_spotify_windows` sending Play straight to Spotify's own SMTC session via `winsdk` on Windows — both bypassing whatever app currently owns generic OS media-key focus. If that finds no running client at all, `_launch_spotify_app` dynamically locates and launches it (Windows: `%APPDATA%\Spotify\Spotify.exe`, the uninstall registry, `PATH`, then the Microsoft Store package via `Get-AppxPackage` + its AUMID; Linux: `PATH` then Flatpak's `com.spotify.Client`) rather than assuming `config/system.json`'s static `spotify`/`spotify.exe` app shortcut is on `PATH`. Only if no install can be found does it fall back to a blind OS media-key press.
- **On Windows every service shows up as two `python` processes — that's expected, not a leak or a duplicate.** The venv is built from the Microsoft Store Python, so `.venv\Scripts\python.exe` is a ~270 KB launcher stub (~10 MB each, ~140 MB across the ~14 services) that spawns the real `python3.12.exe` as its child, and the *child* does all the work (e.g. clDaemon's holds ~1 GB of models). The launcher ties the child's lifetime to its own, so `proc.terminate()` on the stub (what `clJarvis.py`'s `stop_native` and `boot.py`'s sweep do) takes both down. When killing something by hand, kill the stub with `taskkill /PID <pid> /T /F` and never the child alone — the supervisor just respawns it — and match on the script name, not on which interpreter path is shown.
