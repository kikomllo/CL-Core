# Claude voice bridge — core (backends, config dir, requirements)

Read when working on `src/clClaudeBridge.py`, `src/utils/clClaudeSession.py`, `clPtyBridge.py`, `clClaudeTmuxBridge.py`, or `boot.py`'s claude/tmux install. Related: `docs/context/claude-bridge-session.md` (onboarding, speech, stall, sign-in), `docs/context/claude-bridge-widget.md` (dashboard widget, /terminal mode, resize), and the plan in `docs/claude_bridge_plan.md`.

- **Claude voice bridge** (`src/clClaudeBridge.py`): mirrors a real `claude` CLI session into the ecosystem. Voice commands routed by `clDaemon.py`'s Claude-bridge regex (see `route_voice_command`) land on `jarvis/claude/question`; the bridge types that text into a persistent `claude` session as if typed at the keyboard, and mirrors that session's screen back out on `jarvis/claude/screen` for a dashboard widget. Two backends share one `ClaudeSessionBase` (`src/utils/clClaudeSession.py`) holding everything OS-independent — busy/prompt detection, first-run auto-answers and their retry, stall detection, sign-in URL opening, session settings files, and config-dir/`--continue` logic — while each backend owns only spawn, send text, send raw keys, obtain screen text, alive check, and stop. `src/utils/clPtyBridge.py` (`ClaudePtyBridge`) is the Windows backend: ConPTY through `pywinpty`, rendered to plain text through `pyte` since ConPTY only hands back raw ANSI. It spawns the native `claude.exe` bundled inside the npm-installed CLI directly rather than the `claude.cmd` shim — a `.cmd` file's arguments don't survive being spawned straight through `CreateProcess` under ConPTY, so `--continue` was silently getting dropped. `src/utils/clClaudeTmuxBridge.py` (`ClaudeTmuxBridge`) is the Linux backend: tmux resolves the ANSI screen itself (`capture-pane -p -J`), so no terminal-emulation library is needed; a detached `tmux new-session` outlives the bridge process, so a bridge crash/restart reattaches to the same session (`has-session`) instead of losing it, and `pipe-pane` into a FIFO drives event-driven screen updates instead of polling. AUTO_ANSWERS tokens are backend-neutral (`"DOWN ENTER"`, `"ENTER"`); each backend's `_send_control_keys()` maps them to its own encoding — ConPTY escape bytes on Windows, tmux key names (`.title()`'d, e.g. `"Down Enter"`) on Linux. Both backends launch with `--continue` once a prior conversation exists (see below), so a crashed/restarted session recovers its full history rather than starting blank.
- **Isolated config directory, not the default `~/.claude/`.** The bridge sets `CLAUDE_CONFIG_DIR` (documented in Claude Code's own auth docs) to `data/claude_bridge_config/` (gitignored — it holds real credentials) before spawning. This exists specifically because sharing `~/.claude/` with whatever interactive `claude` session a developer happens to have open (e.g. one editing this very repo) triggers a documented lock-contention hang during login (github.com/anthropics/claude-code issues [#91987](https://github.com/anthropics/claude-code/issues/91987), [#63007](https://github.com/anthropics/claude-code/issues/63007)) — a real, reproduced issue during this feature's own development, not a hypothetical. A dedicated config dir means the bridge's process never touches the same files as any other `claude` session at all. There is deliberately no `.env`/Settings credential like Tapo's or Spotify's: `CLAUDE_CODE_OAUTH_TOKEN` only applies to headless `-p` calls and the interactive session ignores it (all `CLAUDE_CODE_*` vars are stripped from the spawn env anyway). The sign-in lives in the config dir instead — see `--setup` in `claude-bridge-session.md`.
- **Every process spawn strips inherited `CLAUDE_CODE_*` env vars** before launching. `child_env = os.environ.copy()` used to carry these straight through from whatever shell launched the ecosystem (e.g. a Claude Code session doing dev work on this very repo) — the spawned `claude` then saw itself as a nested child session and silently disabled transcript saving, which `--continue` itself depends on to have anything to resume.
- **`--continue` is only passed once a real prior conversation exists.** `claude --continue` hard-errors ("No conversation found to continue") and exits immediately if `<config dir>/projects/` doesn't exist yet — true for every first launch against a fresh config dir. `ClaudeSessionBase._should_continue()` checks for that directory (shared by both backends) and the flag is omitted until a real session has actually been recorded there.
- **System requirements, both OSes: the `claude` CLI itself, plus `tmux` on Linux.** Neither is a `requirements.txt` entry (that file is pip-only), so `boot.py` auto-installs both, best-effort and non-fatal like its other optional-feature setup: `_ensure_linux_system_packages()` apt-installs `tmux` and `npm` on Linux (extending the same dict that already covers `pactl`), and `_ensure_claude_cli()` runs on both OSes — installing Node/npm via `winget` first if missing on Windows (same tool `clUpdater.py` already uses for app updates; the freshly-installed dir is added to `os.environ["PATH"]` directly since a winget install's PATH update doesn't reach the already-running boot process), then `npm install -g @anthropic-ai/claude-code` either way. A machine with no `apt-get`/`winget` (or where either step fails) just gets a clear message to install manually; either way `ClaudeTmuxBridge.start()`/`ClaudePtyBridge._resolve_claude_binary()` still check with `shutil.which()` before spawning and raise a clear `FileNotFoundError` naming whichever is missing, rather than the ecosystem supervisor silently respawning a service that can't work.
