# Daemon, routing and actuators

Read when working on `clDaemon.py`, intent routing, `ActionRouter`/`actions.json`, config loading, or an actuator.

- **Central Brain** (`src/clDaemon.py`, class `CentralDaemon`): the dialogue state machine and router. Its core is `route_voice_command()`, which uses **hybrid cognitive routing**:
  1. **Fast-Path** — `nlp/clIntentEngine.py`'s `IntentEngine`, a stateless RapidFuzz fuzzy matcher built from `config/intents.json` templates/priority words (~0.01s).
  2. **Smart-Path** — `nlp/clSLM.py`'s `SLMInferenceEngine`, invoked when the fast-path misses or the request looks compound/corrective. Runs the fine-tuned Qwen2.5-0.5B GGUF through `llama-cpp-python` with `config/grammars/intent_schema.gbnf` grammar-constrained decoding, and also sees recent dialogue history for context (pronoun resolution, corrections).
  3. Falls back to the fuzzy parser again if the SLM is disabled or returns no actions.
  Multi-turn state (e.g. "awaiting Spotify choice") lives in `self.active_context` / `self.dialogue_history`; `intents.json` and `responses.json` are hot-reloaded on mtime change via `_watch_configs`.
- **Proactive follow-ups** (`CentralDaemon._roll_followup`): after a dispatched action, whether to speak a follow-up is a two-stage roll over a weighted candidate pool (`config/core.json` → `settings.followup_settings`), not an always-on "anything else" — `generic` (any time), `lights_off_evening` (no lights on + evening hours), `music_paused` (Spotify not playing). Stage 1 picks a candidate by weight among those currently eligible; stage 2 rolls its own `fire_probability` to decide if it's actually spoken. Each candidate has an independent cooldown (short after any ask, escalated after an explicit decline, tracked in `self.suggestion_cooldowns`), and `system.discovery`'s `discover` action suppresses the whole mechanism (it's already a lengthy, TTS-heavy interaction). `settings.enable_followup = false` disables it entirely. Live light on/off state comes from subscribing to `jarvis/sys/light_status`, separate from the pre-existing `is_spotify_playing` tracking off `jarvis/sys/media_status`.
- **ActionRouter** (`src/utils/clActionRouter.py`, singleton): the single place an `action_id` (e.g. `"light.set"`) — whether it came from the fast-path or the SLM — is translated into an MQTT topic + validated payload, using `config/actions.json` as the registry. Actuators never receive anything except already-routed MQTT messages.
- **Actuators** are independent MQTT subscribers, each owning one integration: `clControl.py` (WiZ/Tapo lights, with MAC-sweep self-healing on IP change), `clSpotify.py` (Spotify Web API, ducking during TTS), `clTerminal.py` (OS-level app/window control), `clTTS.py` (fully local speech via **Piper**, `utils/clTTSEngines.py`: voice `en_GB-aru-medium` speaker 2 at Ryan's pace (`length_scale` 0.8) and its natural pitch — picked by ear in an A/B against the original Ryan voice. A pitch lift (`PIPER_PITCH`, +5% then +2%, done by declaring a slightly higher sample rate and generating proportionally slower) was tried and dropped on the owner's call; 1.0 = off. Audio is streamed chunk-by-chunk into `mixer.Channel(1)` at 24 kHz while the blip plays; only phrases ≤140 chars are cached, as `assets/tts_<hash>_local.wav`, keyed by voice+speaker+pitch so a different voice never replays stale audio. **Resources**: ~300 MB while speaking, the voice is unloaded `settings.tts_piper_idle_seconds` (default 30; 0 = keep loaded) after use (~190 MB left, reload ~2.3 s, started again as soon as `jarvis/sys/mic_state` says the user began speaking so it is ready by the time a reply is needed), and the service itself is ~80-135 MB idle; the model downloads itself into gitignored `models/piper/` on first use. `tts_stop`/`abort` set the engine's `stop` event and stop the channel. `settings.tts_engine = "edge"` puts the cloud edge-tts first (Microsoft began 403-ing it on 2026-10-10). **Pocket TTS (a cloned-Ryan streaming model) was built, measured and removed**: it sounded closest to Ryan but needs PyTorch + ~0.9 GB of RAM that Python cannot hand back once loaded, which the owner ruled out for this lean ecosystem — don't reintroduce a PyTorch-based voice); `clMonitor.py` (single paired-beacon presence — see `docs/context/monitor.md`). `clAutomation.py` reacts to presence events and drives the others through ActionRouter — see `docs/context/automation.md`.
- **ConfigLoader** (`src/utils/clConfigLoader.py`) enforces JSON Schema validation (`config/intents_schema.json` etc.) rather than tolerating malformed config — per `.agents/AGENTS.md`, don't add legacy-compat fallbacks here, keep configs on the strict modern schema.
- **State persistence is mid-migration to Redis** (`src/utils/clRedisClient.py`, pooled client keyed off `REDIS_HOST`/`REDIS_PORT`/`REDIS_DB` in `.env`) — see `tests/test_redis_migration.py` for the target shape when touching persisted daemon/UI state.
- **Lyrics** (`clSpotify.py` `fetch_lyrics`, helpers in `src/utils/clLyrics.py`; published once per track on `jarvis/sys/spotify_lyrics`): providers run in order until one has *synced* lyrics — lrclib first (`/get` with the title as Spotify has it, then without "(feat. …)"-style tags, then one fuzzy `/search`; ≤4 requests per new track) — and the first *plain* text any of them had is the fallback. Plain lyrics reach the UI with **estimated** line times (`estimate_line_times`: spread over the track, weighted by line length; payload `synced: false`) because `LyricsDisplay` only knows the timed three-row karaoke view; `LYRICS_ESTIMATE_UNSYNCED=0` in `.env` shows nothing for them instead. Results, including "nothing found", are cached in `data/lyrics_cache/` (synced entries forever; plain-only/misses re-checked after 7 days or as soon as the provider list changes); a lookup that failed on the network (or was rate-limited) is never cached as a miss. Measured on the owner's library: lrclib has no synced lyrics for much Portuguese rap but does have plain text for many of those tracks. Tests must not touch the real cache (`tests/test_clSpotify.py` autouse-patches `LYRICS_CACHE_DIR`). **Timing gotcha (found live):** the local media session reports a new title a moment *before* its new length (GEIZA arrived with the previous track's 226 s instead of 136 s), and lrclib matches on duration — so a new track's lookup waits `LYRICS_SETTLE_SECONDS` (1.5 s) and uses the duration the local status holds by then, and a lookup that found nothing is repeated once if the duration is later corrected by more than 2 s (`_request_lyrics`/`maybe_publish_lyrics`). **YouTube Music provider** (`src/utils/clYtMusicLyrics.py`, `ytmusicapi`, no login/cookie, on by default; `LYRICS_YTMUSIC_ENABLED=0` turns it off; a missing library only logs a warning): runs when lrclib has no *synced* lyrics — search (songs only) → watch page → lyrics tab with timestamps (sourced from Musixmatch/LyricFind). A result is accepted only if its length is within 5 s of the track and title/artist match (accent/case/credit-insensitive), so another song's lyrics are never shown. Blocking library, so it runs in a worker thread with a 15 s deadline; failures pause it (1 min, 30 min after 3 in a row) and are never cached as misses. Measured on the owner's library it recovered 4 of the 6 tracks lrclib had no synced lyrics for. Rejected alternatives: Spotify's own lyrics endpoint needs the user's `sp_dc` session cookie (browsers now block reading it; the code was written and removed), and Musixmatch's anonymous desktop token only returns a canned sample ("Drake - NOKIA", 0 lines). When the provider list changes the cache re-checks every track that had no synced lyrics.
- **Latency trace** (`src/utils/clLatency.py`): each voice command carries wall-clock stamps mic → Whisper → Daemon (and `jarvis/sys/trace` from TTS when reply audio starts); the Daemon logs two `[LATENCY]` lines per command (at action publish and at reply audio) with the gap before each stage. Check `logs/latest_run.log` after touching the voice path.
- SLM model paths/URLs and the training pipeline: see `training/CLAUDE.md`.
