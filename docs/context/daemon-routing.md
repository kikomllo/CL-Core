# Daemon, routing and actuators

Read when working on `clDaemon.py`, intent routing, `ActionRouter`/`actions.json`, config loading, or an actuator.

- **Central Brain** (`src/clDaemon.py`, class `CentralDaemon`): the dialogue state machine and router. Its core is `route_voice_command()`, which uses **hybrid cognitive routing**:
  1. **Fast-Path** — `nlp/clIntentEngine.py`'s `IntentEngine`, a stateless RapidFuzz fuzzy matcher built from `config/intents.json` templates/priority words (~0.01s).
  2. **Smart-Path** — `nlp/clSLM.py`'s `SLMInferenceEngine`, invoked when the fast-path misses or the request looks compound/corrective. Runs the fine-tuned Qwen2.5-0.5B GGUF through `llama-cpp-python` with `config/grammars/intent_schema.gbnf` grammar-constrained decoding, and also sees recent dialogue history for context (pronoun resolution, corrections).
  3. Falls back to the fuzzy parser again if the SLM is disabled or returns no actions.
  Multi-turn state (e.g. "awaiting Spotify choice") lives in `self.active_context` / `self.dialogue_history`; `intents.json` and `responses.json` are hot-reloaded on mtime change via `_watch_configs`.
- **Abort vs commands containing an abort word** (`src/utils/clAbort.py`, used by `IntentEngine.is_abort_command` — the daemon's "global abort" pass that runs before intent matching — and by `clWhisper.py`'s instant abort): a phrase is an abort only when it is made of abort words (`nlp_rules.abort_keywords`: abort, cancel, nevermind, stop) and filler ("hey jarvis", "that", "please", "sequence" ...). It used to be a substring test, so "cancel all alarms", "cancel reminder", "stop the music" and "cancel reminder and remind me in 10 minutes" were swallowed as bare aborts and did nothing (live log, 2026-10-13); they now route to `alarm.control`, `reminder.delete`(+`reminder.create`) and `spotify.control`. Reminders without a recording are no longer pre-generated with cloud edge-tts (403): `clReminderTrigger.py` speaks the text with the local voice when it fires, and a reminder with no task text says "you asked me to remind you" instead of repeating its time phrase.
- **Proactive follow-ups** (`CentralDaemon._roll_followup`): after a dispatched action, whether to speak a follow-up is a two-stage roll over a weighted candidate pool (`config/core.json` → `settings.followup_settings`), not an always-on "anything else" — `generic` (any time), `lights_off_evening` (no lights on + evening hours), `music_paused` (Spotify not playing). Stage 1 picks a candidate by weight among those currently eligible; stage 2 rolls its own `fire_probability` to decide if it's actually spoken. Each candidate has an independent cooldown (short after any ask, escalated after an explicit decline, tracked in `self.suggestion_cooldowns`), and `system.discovery`'s `discover` action suppresses the whole mechanism (it's already a lengthy, TTS-heavy interaction). `settings.enable_followup = false` disables it entirely. Live light on/off state comes from subscribing to `jarvis/sys/light_status`, separate from the pre-existing `is_spotify_playing` tracking off `jarvis/sys/media_status`.
- **Powering the computer off by voice** (`src/utils/clConfirm.py`, `clDaemon.py`, `clTerminal.py`; tests `tests/test_voicePoweroff.py`): three gates and a way out. (1) Only an **exact phrase** asks (`is_shutdown_request`: "shut down / turn off / power off the computer or pc", with my/the/this, please/now, an optional wake word): it is checked after the interactive contexts and before any fuzzy matching, because the fuzzy fast path took "shut down the heater" and "turn off the computer screen" for it; there is deliberately **no intent in `intents.json` and the SLM grammar does not know the action**, so neither can produce it (a test pins both). (2) The daemon only **asks** ("Shut down the computer, sir? Say yes to confirm.", `request_reply`, `ignore_silent`, context `poweroff_confirm` for 20 s); only a clear yes (`is_affirmative`: yes/yeah/confirm/do it/go ahead, with filler only; any negative word, "okay" or "sure" does not count) sends `terminal.shutdown` with a **20 s delay**, and `_authorise_dispatch` lets that action through only with the one-shot authorisation that yes set, so nothing else can send it. (3) The delay lives in `clTerminal.py` (`threading.Timer`, dropped if the service restarts, which is the safe failure) and **any abort** ("cancel", "stop", the abort topic) cancels it; `terminal.cancel_shutdown` does too. Windows `shutdown /s /t 0`, Linux `shutdown now`. `system.speak` now forwards `ignore_silent` (it was silently dropped by the router before, so the prompts that asked for it were muted in silent mode).
- **ActionRouter** (`src/utils/clActionRouter.py`, singleton): the single place an `action_id` (e.g. `"light.set"`) — whether it came from the fast-path or the SLM — is translated into an MQTT topic + validated payload, using `config/actions.json` as the registry. Actuators never receive anything except already-routed MQTT messages.
- **"restart <module>"** (`system.restart_module` → `jarvis/sys/manager` → `clJarvis.py`, matching in `src/utils/clModuleMatch.py`): a target restarts its first matching enabled service; a generic UI target (`ui`, `dashboard`, `interface`...) restarts every enabled UI service (Web UI server, then the Desktop Shell window, or the Qt UI if that is the one on). It used to stop at the first match, the Web UI server, which the open page silently reconnected to, so "restart ui module" appeared to do nothing. Tests: `tests/test_clModuleMatch.py`. The supervisor itself is not restarted by this: a change to `clJarvis.py` needs a full ecosystem restart.
- **Actuators** are independent MQTT subscribers, each owning one integration: `clControl.py` (WiZ/Tapo lights, with MAC-sweep self-healing on IP change), `clSpotify.py` (Spotify Web API, ducking during TTS), `clTerminal.py` (OS-level app/window control), `clTTS.py` (fully local speech via **Piper**, `utils/clTTSEngines.py`: voice `en_GB-aru-medium` speaker 2 at Ryan's pace (`length_scale` 0.8) and its natural pitch — picked by ear in an A/B against the original Ryan voice. A pitch lift (`PIPER_PITCH`, +5% then +2%, done by declaring a slightly higher sample rate and generating proportionally slower) was tried and dropped on the owner's call; 1.0 = off. Audio is streamed chunk-by-chunk into `mixer.Channel(1)` at 24 kHz while the blip plays; only phrases ≤140 chars are cached, as `assets/tts_cache/tts_<hash>_local.wav`, keyed by voice+speaker+pitch (or Kokoro blend+speed) so a different voice never replays stale audio; the cache keeps 1000 phrases (`CACHE_MAX_FILES`, least recently used go first, a replay refreshes the file). **The real Ryan edge-tts mp3s live in `assets/ryan/` and are never pruned** (they cannot be regenerated while edge-tts is blocked; edge mode reads and writes there, and still finds loose legacy ones in `assets/`); `migrate_legacy_files()` moves anything left loose in `assets/` into the right folder on every service start. Both folders are gitignored — back `assets/ryan/` up if it matters. **Resources**: ~300 MB while speaking, the voice is unloaded `settings.tts_piper_idle_seconds` (default 30; 0 = keep loaded) after use (~190 MB left, reload ~2.3 s, started again as soon as `jarvis/sys/mic_state` says the user began speaking so it is ready by the time a reply is needed), and the service itself is ~80-135 MB idle; the model downloads itself into gitignored `models/piper/` on first use. `tts_stop`/`abort` set the engine's `stop` event and stop the channel. `settings.tts_engine = "kokoro"` (**the owner's main voice**) makes **Kokoro-82M** (int8 ONNX, no PyTorch) speak instead, Piper staying the fallback: an equal blend of the British male styles `bm_fable`+`bm_lewis` at speed 1.3, natural pitch, sentence-final "." turned into "!" (`settings.tts_kokoro_bright`, default on) because it reads brighter; chosen by ear and by measured pitch movement (Ryan 4.2 semitones, Daniel 1.7 = "dead", Fable 3.3). It is generated one sentence at a time (`split_pieces`) so audio starts after ~1.1-1.9 s (real-time factor ~0.45) — **that speed needs onnxruntime 1.31; 1.26 was 3.5x slower** (first audio ~4 s). ~400 MB while loaded, ~110 MB once unloaded; models (`kokoro-v1.0.int8.onnx` + `voices-v1.0.bin`, ~120 MB) download into gitignored `models/kokoro/` on first use; `settings.tts_idle_seconds` (old name `tts_piper_idle_seconds`) unloads whichever engine is loaded — default 90 s for Kokoro (it keeps a conversation and proactive replies like alarms warm; a mic event only warms it for voice commands), 30 s for Piper. At boot `preload()` also runs one throwaway sentence (`KokoroEngine.warm_up`, once per process) because the first inference in a process is ~1.5 s slower. A first sentence over 90 characters is cut at its first comma (`KOKORO_FIRST_SPLIT`) so audio starts after the first clause. Kokoro speaks ~10 dB quieter than Piper (-23 vs -13 dBFS RMS; real Ryan -20), so its output gets a fixed +7 dB (`KOKORO_GAIN_DB`) through a look-ahead peak limiter (`boost`, ceiling 0.95, ~20 ms) to land near -16 dBFS without clipping; the gain is part of the cache tag. The EchoGuard volume (`data/barge_in_state.json` gain) multiplies on top — check it is 1.00 before blaming the voice for being quiet. Piper stays the default when `tts_engine` is unset. **`settings.tts_engine = "ultron"`** (`UltronEngine`, the Ultron voice) is Piper plus the `utils/clVoice.py` effect chain applied per sentence inside the stream (so streaming, barge-in and idle unload work as for the other engines): the voice is `settings.tts_settings.piper_model` (the trained `actor_voice.onnx`; the stock Piper voice speaks, with a warning, if that file is missing), `tts_settings.fx_level` is `off` (dry), `light` (pitch drop + EQ + drive + reverb; no denoise/vocoder/comb/ring mod, the lite-profile default) or `full`, and a sentence's reverb tail is mixed into the next sentence instead of ending each one in its own echo. Piper is the fallback if it fails; the cache tag hashes the whole `tts_settings`. Measure with `python training/tools/bench_tts.py` (first-chunk latency, real-time factor, RAM; `--wav-dir` saves the renders). Plan: `docs/ultron_plan.md`. **Pre-render:** `TTSManager.prerender()` renders every fixed (no `{placeholder}`) phrase of `responses.json` (all three sections, <=140 chars) into the phrase cache with the primary voice, so those replies are a file read; it runs once ~60 s after the service starts (`settings.tts_prerender`, default on), waits while a reply is spoken or the mic is active, does nothing and loads nothing when everything is cached, and re-runs by itself after a voice or `tts_settings` change (the cache tag changes). Manual: `python src/clTTS.py --prerender` (52 phrases / 57 s with Kokoro on the desktop). Phrases with `{placeholders}` and the reply model's free text are not covered. `settings.tts_engine = "edge"` puts the cloud edge-tts first (Microsoft began 403-ing it on 2026-10-10). **Pocket TTS (a cloned-Ryan streaming model) was built, measured and removed**: it sounded closest to Ryan but needs PyTorch + ~0.9 GB of RAM that Python cannot hand back once loaded, which the owner ruled out for this lean ecosystem — don't reintroduce a PyTorch-based voice); `clMonitor.py` (single paired-beacon presence — see `docs/context/monitor.md`). `clAutomation.py` reacts to presence events and drives the others through ActionRouter — see `docs/context/automation.md`.
- **ConfigLoader** (`src/utils/clConfigLoader.py`) enforces JSON Schema validation (`config/intents_schema.json` etc.) rather than tolerating malformed config — per `.agents/AGENTS.md`, don't add legacy-compat fallbacks here, keep configs on the strict modern schema. **`config/core.json` is per-machine and gitignored** (services rewrite it at runtime and it holds audio devices, `hardware`, `stt_model`); the tracked template is `config/core.default.json`. `src/utils/clLocalConfig.py` creates `core.json` from it and adds keys the template gained later, never overwriting a value (`clJarvis.py` runs it at start, `ConfigLoader.load_json` and the test `conftest` too); a new core setting therefore goes in the template. `python src/utils/clLocalConfig.py --profile lite|full` applies a hardware tier from `config/profiles.json` (lite = integrated graphics / 12 GB: CPU Whisper `base`, Piper, no GPU layers) and records `settings.performance_profile`. Pulling the commit that untracked `core.json` makes git delete or refuse a machine's existing copy: back it up first, restore after.
- **State persistence is mid-migration to Redis** (`src/utils/clRedisClient.py`, pooled client keyed off `REDIS_HOST`/`REDIS_PORT`/`REDIS_DB` in `.env`) — see `tests/test_redis_migration.py` for the target shape when touching persisted daemon/UI state.
- **Lyrics** (`clSpotify.py` `fetch_lyrics`, helpers in `src/utils/clLyrics.py`; published once per track on `jarvis/sys/spotify_lyrics`): providers run in order until one has *synced* lyrics — lrclib first (`/get` with the title as Spotify has it, then without "(feat. …)"-style tags, then one fuzzy `/search`; ≤4 requests per new track) — and the first *plain* text any of them had is the fallback. Plain lyrics reach the UI with **estimated** line times (`estimate_line_times`: spread over the track, weighted by line length; payload `synced: false`) because `LyricsDisplay` only knows the timed three-row karaoke view; `LYRICS_ESTIMATE_UNSYNCED=0` in `.env` shows nothing for them instead. Results, including "nothing found", are cached in `data/lyrics_cache/` (synced entries forever; plain-only/misses re-checked after 7 days or as soon as the provider list changes); a lookup that failed on the network (or was rate-limited) is never cached as a miss. Measured on the owner's library: lrclib has no synced lyrics for much Portuguese rap but does have plain text for many of those tracks. Tests must not touch the real cache (`tests/test_clSpotify.py` autouse-patches `LYRICS_CACHE_DIR`). **Timing gotcha (found live):** the local media session reports a new title a moment *before* its new length (GEIZA arrived with the previous track's 226 s instead of 136 s), and lrclib matches on duration — so a new track's lookup waits `LYRICS_SETTLE_SECONDS` (1.5 s) and uses the duration the local status holds by then, and a lookup that found nothing is repeated once if the duration is later corrected by more than 2 s (`_request_lyrics`/`maybe_publish_lyrics`). **YouTube Music provider** (`src/utils/clYtMusicLyrics.py`, `ytmusicapi`, no login/cookie, on by default; `LYRICS_YTMUSIC_ENABLED=0` turns it off; a missing library only logs a warning): runs when lrclib has no *synced* lyrics — search (songs only) → watch page → lyrics tab with timestamps (sourced from Musixmatch/LyricFind). A result is accepted only if its length is within 5 s of the track and title/artist match (accent/case/credit-insensitive), so another song's lyrics are never shown. Blocking library, so it runs in a worker thread with a 15 s deadline; failures pause it (1 min, 30 min after 3 in a row) and are never cached as misses. Measured on the owner's library it recovered 4 of the 6 tracks lrclib had no synced lyrics for. Rejected alternatives: Spotify's own lyrics endpoint needs the user's `sp_dc` session cookie (browsers now block reading it; the code was written and removed), and Musixmatch's anonymous desktop token only returns a canned sample ("Drake - NOKIA", 0 lines). When the provider list changes the cache re-checks every track that had no synced lyrics.
- **Ducking trigger**: `tts_state:active` (published as soon as a reply is queued, locks the mic, drives the UI) no longer ducks Spotify by itself — a slow voice used to leave seconds of quiet music-less silence while synthesizing (worst for long Claude-bridge replies). `clTTS` publishes `jarvis/sys/tts_audio {"state":"ready"}` once the first audio exists (just before the blip); the Daemon ducks only when `tts_state == active` **and** `tts_audio_ready`, and clears the flag on every `tts_state` message.
- **Latency trace** (`src/utils/clLatency.py`): each voice command carries wall-clock stamps mic → Whisper → Daemon (and `jarvis/sys/trace` from TTS when reply audio starts); the Daemon logs two `[LATENCY]` lines per command (at action publish and at reply audio) with the gap before each stage. Check `logs/latest_run.log` after touching the voice path.
- SLM model paths/URLs and the training pipeline: see `training/CLAUDE.md`.
- **Light colour and capability** (`src/clControl.py`): `light.set` carries `color` (a name from `config/entities.json`), `rgb` (`[r, g, b]`, validated 0-255 before any light is touched; an explicit rgb beats a name), `temp` (0-100 mapped to each brand's kelvin range: WiZ 2700-6500, Tapo 2500-6500), `lum`. **`ActionRouter` forwards only fields listed in `actions.json`'s schema**, so a new payload field must be added there or it silently vanishes. pywizlight rescales an rgb inside `PilotBuilder` (150,60,220 becomes 143,0,255): compare with the library's own output in tests, not with the input. `jarvis/sys/light_status` per light: `name`, `is_on`, `offline`, `brand`, `colour` (capability), `brightness` (%), and either `rgb` (colour mode) or `kelvin` (white mode; a Tapo bulb reports `color_temp` 0 in colour mode). Capability: the light's own `"colour": true/false` in `devices.json` wins, then WiZ `bulbtype.features.color`, then Tapo `TAPO_MODEL` (l510/l520/l610 white-only), and an unknown light gets the button. Tests: `TestExplicitRgb`, `TestLightStatusColourFields` in `tests/test_clControl.py`. **Tapo connection handling** (`LightManager._tapo_call`): a bulb allows one session at a time and the Tapo library (Rust) ignores asyncio cancellation, so every call to a bulb goes through one per-IP lock, reuses its logged-in handle (dropped on any error; a session/handshake error is retried once, nothing else, so a toggle never runs twice) and is cut off after `TAPO_TIMEOUT` by `_bounded`, which abandons the call in the background (`asyncio.wait_for` would wait ~20 s for the library's own connect timeout). Without this a toggle overlapping a poll gave `SESSION_TIMEOUT`/`Handshake2 failed`, and a bulb that dropped off Wi-Fi froze the Lights window. `poll_light_status` re-polls every `POLL_INTERVAL` (25 s) as well as on `poll_trigger`; a failed poll publishes `is_on: null` (the window says "Not responding…") until the third miss makes it `offline`; every command, successful or not, triggers a re-poll and its result goes out through `_publish_feedback` (fresh connection if the listener's is dead). Tests: `TestTapoSessionHandling`, `TestPollingResilience`, `TestFeedbackDelivery`.
- **Which light?** (`light_target_clarify` context): a light command with no usable target is asked about instead of guessed. Two sources: (1) `clControl.py` `unknown_target` — a named light that matches none of the saved ones (it used to fall through to the legacy default bulb, silently the wrong light) publishes `jarvis/feedback` `action: request_light_target` with a `message` listing the saved lights and the `pending` command (`action/color/lum/temp/rgb`); (2) the daemon's `_expire_partial` for a cut-off "turn on the" nobody finished. The daemon speaks it with `request_reply`, and the answer re-sends `light.set` with `light_target` set (`_spoken_light_target`: an all-word (all/everything/both…) means `all`; filler like "the"/"in the" is stripped). An answer that parses as a command of its own ("play music") is routed as that command instead, and "everything" is checked first because it alone parses as `system.restart_all`. After two asks in a row (60 s) it says it still can't tell and leaves the lights alone. "turn on the lights" with no name still means all lights by design (`actions.json` default). Tests: `tests/test_clDaemon.py::TestWhichLightQuestion`, `tests/test_clControl.py::TestUnknownLightTarget`.
