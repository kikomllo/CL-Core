# Claude voice bridge — session behavior (onboarding, speech, stalls, sign-in)

Read when working on first-run auto-answers, speech output, the stall watchdog, or sign-in. Backends and config dir: `docs/context/claude-bridge-core.md`.

- **First-run screens are auto-answered** by `ClaudeSessionBase._maybe_auto_answer()` off the shared `AUTO_ANSWERS` rule table (marker text on screen → backend-neutral token): the theme picker and login-method menu (both already highlight the right option — Dark / "Claude account with subscription" — so plain `"ENTER"`), every "Press Enter to continue" (login success, security notes), and the "trust this folder?" menu. The trust menu is an arrow-key list defaulting to `❯ No, exit`, so typing text + Enter would confirm "No" and quit; it needs a down arrow plus Enter (token `"DOWN ENTER"`) sent via `send_keys()` (raw control sequences, unlike `write()` which types a line and submits it) — on Windows this is the application-mode escape `\x1bOB\r` (not the normal-mode `\x1b[B` — this TUI runs with application cursor keys enabled), on Linux it's tmux's own `Down`/`Enter` key names, which tmux resolves to the right escape itself. Back-to-back screens with the same marker are told apart by the whole screen text, and an Enter dropped while the TUI was redrawing (same screen, no new output for 3s) is retried up to 3 times. Trust state persists in the config dir, so it doesn't recur.
- **Speech is the bridge's job, not the session's.** A `Stop` hook (`src/utils/clClaudeStopHook.py`) receives the finished turn's `last_assistant_message` from the CLI and publishes it to `jarvis/claude/reply`; `clClaudeBridge.py` strips code/tables/markdown/URLs (`speakable_text`, capped at 800 chars on a sentence boundary), and publishes to `jarvis/sys/speak` with `claude_session: true`, plus `request_reply` when the answer ends in a question so the daemon re-opens the mic for a spoken answer. It deliberately does *not* set `ignore_silent`, so silent mode mutes it (and makes audible-free testing possible). The hook and an appended system prompt (`--append-system-prompt-file`) are passed per launch via `--settings`/CLI flags generated into the config dir, so they never touch a developer's own `claude` sessions. Because the model still sometimes ran the repo's standing speak command itself (doubling every answer), a `PreToolUse` hook (`--block-speak`) refuses any Bash command mentioning `jarvis/sys/speak` in the bridged session, and the standing instruction in the root `CLAUDE.md` defers to the bridge.
- **Stall watchdog and readiness.** `ClaudeSessionBase.process_screen()` (fed a fully-resolved screen by either backend) tracks two flags off every snapshot: busy (`esc to interrupt` in the footer) and at-the-idle-prompt (a `❯` row bracketed by horizontal rules — menus reuse `❯` but have no rules). A busy session that emits no bytes for 60s is hung (a working one redraws its spinner constantly): `on_stall` fires, and `clClaudeBridge.py` kills the session, restarts it (`--continue` resumes the conversation), waits for the idle prompt, and re-sends the last question once — the retried question shows up twice in the transcript, which is accepted over dropping it. The same readiness wait gates the first injection into any freshly started session, since input typed while the TUI is still booting gets dropped. Root cause of the underlying hang (first found on Windows) was never determined (process alive, no children, no output); this is recovery, not a fix.
- **Sign-in: via the dashboard widget, or one-time via `python src/clClaudeBridge.py --setup`.** The bridge authenticates from `data/claude_bridge_config/.credentials.json` (written by a real browser sign-in), not from any env var. Missing credentials are no longer a hard blocker on `ClaudeBridgeService.run()` — the live service starts the session anyway (`force_fresh=True` on that first start only, so it never silently reattaches to a stale session an earlier aborted attempt left behind, e.g. one stuck on an expired OAuth prompt): the trust/theme/login screens auto-answer themselves, the sign-in URL opens in the browser automatically, and the dashboard's Claude widget (mirroring `jarvis/claude/screen`) shows the resulting `Paste code here` prompt for you to paste the code into directly, via `jarvis/claude/question`. `--setup` (also `force_fresh`-guarded) remains for a pure-terminal alternative — running it while the live bridge is *also* running is still the documented lock-contention risk (a second `claude` process against the same config dir; the cause of this feature's very first stall on Windows), so use one path or the other, not both at once. The browser authorization click itself can never be automated.
