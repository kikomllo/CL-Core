# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

CL-Core ("JARVIS Smart Home OS") is an async, local-first home-automation and NLP system built on an MQTT pub/sub backbone. Every service is an independent process that talks to every other service only through MQTT topics — never through direct imports of another service's code.

## Commands

- **Boot the full ecosystem**: `python boot.py` — creates/updates the venv from `requirements.txt`, takes a single-instance lock on port 64000 (killing any stale ecosystem processes), then execs `clJarvis.py`. `python clJarvis.py` runs the supervisor directly if the venv is already set up.
- **Run one microservice standalone** (for debugging): `python src/clDaemon.py`, `python src/clWhisper.py`, `python src/clControl.py`, etc. — run from the repo root; each service path-hacks `sys.path` to reach `src/utils` and `src/nlp`.
- **Bypass the microphone** for text-only NLP testing: `python src/clDebug.py`.
- **Tests**: `pytest` from the repo root. Single test: `pytest tests/test_clDaemon.py::TestClass::test_name -v` or `pytest -k pattern`. `tests/conftest.py` provides `mock_mqtt` (mocks `aiomqtt.Client` — no real broker needed) and `message_stream`. Async tests are marked explicitly with `@pytest.mark.asyncio`.
- **Bundle source for external LLM review**: `python clBundler.py [file ...]` → `outputs/jarvis_ai_review.txt` (defaults to the root runner + everything under `src/`, `src/utils/`, `src/nlp/`, `config/*.json`).

### SLM fine-tuning pipeline (`training/`)

Everything training-related — dataset generators, Kaggle/Colab notebook scripts, benchmark tooling, and the generated `.jsonl` datasets themselves — lives under `training/` (`training/tools/`, `training/data/`), deliberately separated from the runtime ecosystem so it reads as its own self-contained sub-project. `config/intents.json` and `config/grammars/intent_schema.gbnf` stay in `config/` regardless, since both are also consumed at runtime (`nlp/clIntentEngine.py`, `nlp/clSLM.py`) — only `training/tools/gen_dataset.py` writes to the latter. A dedicated `training/.venv` (or `.venv-train` before it's relocated) holds the heavy training-only dependencies (`torch`, `unsloth`, `bitsandbytes`, `trl`, `peft`, `accelerate`) — kept out of the main ecosystem venv entirely, since runtime inference only ever needs `llama-cpp-python`, not a training stack.

There are two separate models: the **action model** (Qwen2.5-0.5B-Instruct, grammar-constrained, classifies intent into `action_id`/args) and the **reply model** (SmolLM2-360M-Instruct, no grammar, phrases a spoken JARVIS-voiced confirmation for an already-decided action). A change to `config/intents.json` — a new intent, a changed template — generally needs both models regenerated and retrained together, since the action model's grammar and the reply model's phrase bank both key off the same intent set.

1. `python training/tools/gen_dataset.py` — regenerates **both** `training/data/synthetic_lora_dataset.jsonl` and `config/grammars/intent_schema.gbnf` (the action model's inputs) from `config/intents.json` in one pass. These two outputs must stay in lockstep, so the `.gbnf` file is auto-generated and headed "do not hand-edit" — its `action_id`/`action` enums are derived directly from `intents.json`. Change intents, then re-run this script; never hand-edit the grammar.
2. `python training/tools/gen_reply_dataset.py` — regenerates `training/data/reply_lora_dataset.jsonl` (the reply model's input) from `config/intents.json` plus its own hand-written `PHRASE_BANK`/`SLOTTED_PHRASES`/`FOLLOWUP_PHRASES` in the script. A new intent needs a `PHRASE_BANK` entry here to get a spoken confirmation at all; without one it's silently skipped. `training/tools/listen_reply_samples.py` plays samples from this dataset aloud (matching the live TTS voice exactly) to judge phrasing/tone before committing to a retrain.
3. Training — either copy cells into a Kaggle (or Colab) notebook, or run locally against a CUDA GPU using `training/.venv`:
   - `training/tools/kaggle_train_all.py` — trains **both** models in one run (action model, then frees GPU memory, then reply model); the normal path when both datasets changed together. On Kaggle/Colab, needs both `.jsonl` files added as notebook inputs; run locally, it finds them under `training/data/` automatically.
   - `training/tools/kaggle_train.py` / `training/tools/kaggle_reply_train.py` — the same two phases as standalone scripts, for retraining just one model.
4. `python training/tools/benchmark_slm.py` — runs `training/data/benchmark_suite.json` against the action model's GGUF under `config/grammars/intent_schema.gbnf` (grammar-constrained decoding via `llama-cpp-python`) and reports per-category pass rates. Run this before promoting a new GGUF into `config/core.json`'s `slm_settings.model_path` (the reply model has no equivalent pass/fail benchmark — judge it by ear via `listen_reply_samples.py` instead, and point `reply_slm_settings.model_path` at it once trained).

## Architecture

- **Entry point**: `boot.py` → `clJarvis.py`. `clJarvis.py` is the master supervisor: spawns every microservice as a subprocess, tracks health, restarts crashed modules, and can trigger a full ecosystem reboot via an MQTT directive on `jarvis/sys/manager`. Its `TeeLogger` relays every subprocess's stdout to both the console and `logs/latest_run.log` on a per-thread reader; the console side writes through the OS's legacy codepage (cp1252 on Windows), which can't encode a lot of real subprocess output (box-drawing, spinners, emoji) — `reconfigure(errors="replace")` is applied to that stream so an unencodable character gets substituted instead of raising and permanently killing that one subprocess's log relay thread (which happened silently and looked like the subprocess itself had hung, when it was actually still running fine).
- **Central Brain** (`src/clDaemon.py`, class `CentralDaemon`): the dialogue state machine and router. Its core is `route_voice_command()`, which uses **hybrid cognitive routing**:
  1. **Fast-Path** — `nlp/clIntentEngine.py`'s `IntentEngine`, a stateless RapidFuzz fuzzy matcher built from `config/intents.json` templates/priority words (~0.01s).
  2. **Smart-Path** — `nlp/clSLM.py`'s `SLMInferenceEngine`, invoked when the fast-path misses or the request looks compound/corrective. Runs the fine-tuned Qwen2.5-0.5B GGUF through `llama-cpp-python` with `config/grammars/intent_schema.gbnf` grammar-constrained decoding, and also sees recent dialogue history for context (pronoun resolution, corrections).
  3. Falls back to the fuzzy parser again if the SLM is disabled or returns no actions.
  Multi-turn state (e.g. "awaiting Spotify choice") lives in `self.active_context` / `self.dialogue_history`; `intents.json` and `responses.json` are hot-reloaded on mtime change via `_watch_configs`.
- **Proactive follow-ups** (`CentralDaemon._roll_followup`): after a dispatched action, whether to speak a follow-up is a two-stage roll over a weighted candidate pool (`config/core.json` → `settings.followup_settings`), not an always-on "anything else" — `generic` (any time), `lights_off_evening` (no lights on + evening hours), `music_paused` (Spotify not playing). Stage 1 picks a candidate by weight among those currently eligible; stage 2 rolls its own `fire_probability` to decide if it's actually spoken. Each candidate has an independent cooldown (short after any ask, escalated after an explicit decline, tracked in `self.suggestion_cooldowns`), and `system.discovery`'s `discover` action suppresses the whole mechanism (it's already a lengthy, TTS-heavy interaction). `settings.enable_followup = false` disables it entirely. Live light on/off state comes from subscribing to `jarvis/sys/light_status`, separate from the pre-existing `is_spotify_playing` tracking off `jarvis/sys/media_status`.
- **ActionRouter** (`src/utils/clActionRouter.py`, singleton): the single place an `action_id` (e.g. `"light.set"`) — whether it came from the fast-path or the SLM — is translated into an MQTT topic + validated payload, using `config/actions.json` as the registry. Actuators never receive anything except already-routed MQTT messages.
- **Actuators** are independent MQTT subscribers, each owning one integration: `clControl.py` (WiZ/Tapo lights, with MAC-sweep self-healing on IP change), `clSpotify.py` (Spotify Web API, ducking during TTS), `clTerminal.py` (OS-level app/window control), `clTTS.py` (edge-tts speech + playback mixer), `clMonitor.py` (BLE presence).
- **Cross-platform parity**: this is a dual-OS codebase (Linux and Windows dev machines both run the full ecosystem), so OS-specific actions in `clTerminal.py` branch on `CURRENT_OS` rather than assuming Linux. Volume (`pycaw`/Core Audio on Windows vs. `wpctl`/`pactl`/`amixer` on Linux), media control (synthetic `VK_MEDIA_*` key events on Windows vs. `playerctl` on Linux — Windows has no OS-level play/pause split, only a toggle), and eco/DPMS mode (`ctypes` `SC_MONITORPOWER` + a synthetic mouse-nudge to wake on Windows vs. `xset dpms` on Linux) all have both branches implemented. `clReminderTrigger.py`'s desktop notification (a hidden PowerShell `System.Windows.Forms.NotifyIcon` balloon on Windows vs. `notify-send` on Linux) and volume read (`pycaw` vs. `amixer`) follow the same pattern. `pycaw`/`comtypes`/`winsdk` in `requirements.txt` are marked `sys_platform == 'win32'`-only. `clTerminal.py`'s `poll_media_status` background task publishes free, local "now playing" state to `jarvis/sys/os_media_status` on both OSes — `playerctl` (MPRIS) on Linux, SMTC (`winsdk`'s `GlobalSystemMediaTransportControlsSessionManager`) on Windows — whichever app the OS considers current, not necessarily Spotify. `poll_spotify_local_status` runs alongside it, filtering that same free/local source down to Spotify specifically (an MPRIS player named `spotify` on Linux; the SMTC session whose app user model ID contains "spotify" on Windows, found by scanning every session rather than trusting whichever one the OS calls "current") and publishing to `jarvis/sys/spotify_local_status`. `clSpotify.py`'s `status(lightweight=True)` prefers that free local reading over a real API call whenever it's fresh and reports `found: true`, falling back to the Spotify Web API otherwise (including whenever playback is happening on a different Spotify Connect device, which the local OS session can't see) — this is what keeps the ecosystem's most frequent Spotify status polling from burning API quota. Volume has no local-OS equivalent at all (SMTC has no percentage-based volume property, and the OS per-app mixer level isn't the same number as Spotify Connect's own device volume), so it always comes from `last_known_normal_volume` in this fast path, kept accurate by `clSpotify.py`'s own volume/duck actions rather than by polling. `clSpotify.py` reserves real Spotify Web API calls for actually issuing playback commands and reading volume — and it has real rate limits, see its `_check_rate_limit`.
- **Process-sweep fallback**: `boot.py`'s single-instance restart sweep and `clHealth.py`'s Native UI status check both use `wmic` to find/kill processes by command line on Windows, with a `Get-CimInstance`-based PowerShell fallback for machines where `wmic` (deprecated by Microsoft) has been removed.
- **Alarm/reminder scheduling** (`src/clUtilities.py`'s `schedule_systemd_timer`): Linux uses `systemd-run --user --on-calendar=`, a real wall-clock trigger that survives DST shifts and system sleep. The Windows equivalent, `_schedule_windows_task`, builds a Task Scheduler XML task (`WakeToRun`/`StartWhenAvailable` enabled) instead of the old `time.sleep()`-in-a-detached-process approach, which drifted across DST and simply didn't fire if the machine was asleep at the target time. Cancellation on both platforms goes through `cancel_scheduled_timer` (`schtasks /Delete` vs. `systemctl --user stop`/`reset-failed`) rather than assuming `systemctl` exists.
- **WiFi SSID detection** (`src/utils/clNetworkUtils.py`'s `get_current_wifi_ssid`, consumed by `clControl.py` to pick a per-network light profile out of `config/devices.json`'s `networks` map): Linux uses `iwgetid`/`nmcli`; Windows uses `netsh wlan show interfaces` to read the literal broadcast SSID — not `Get-NetConnectionProfile`'s connection *profile name*, which Windows seeds from the SSID but a user can rename independently, and which fails outright on non-English Windows builds where the default adapter alias isn't "Wi-Fi".
- **Push-to-talk key resolution** (`src/clKeybinds.py`): evdev (Linux) resolves any `KEY_*` name generically via `getattr(ecodes, ...)`; pynput (the only backend Windows ever runs) has no equivalent, so `PTT_KEY_MAP`/`is_ptt_key` explicitly map the realistic set of single-key PTT candidates — Ctrl/Shift/Alt variants, Caps Lock, Space, F13–F24 — to pynput `Key` members. Hotkey dedup is state-based only on both backends (evdev's `active_hardware_actions`, pynput's `active_actions`) with no artificial minimum re-trigger interval, so a full release-then-repress fires immediately on both.
- **Spotify wakeup/launch** (`src/clSpotify.py`): `_wake_up_spotify` escalates in stages when nothing is playing. First it targets an already-running client directly — D-Bus's `org.mpris.MediaPlayer2.spotify` name on Linux, or `_wake_up_spotify_windows` sending Play straight to Spotify's own SMTC session via `winsdk` on Windows — both bypassing whatever app currently owns generic OS media-key focus. If that finds no running client at all, `_launch_spotify_app` dynamically locates and launches it (Windows: `%APPDATA%\Spotify\Spotify.exe`, the uninstall registry, `PATH`, then the Microsoft Store package via `Get-AppxPackage` + its AUMID; Linux: `PATH` then Flatpak's `com.spotify.Client`) rather than assuming `config/system.json`'s static `spotify`/`spotify.exe` app shortcut is on `PATH`. Only if no install can be found does it fall back to a blind OS media-key press.
- **Dashboard window-flag parity** (`src/clUI.py`): the fullscreen dashboard no longer sets `WindowStaysOnTopHint` on Windows — that was only safe alongside a Windows-only background occlusion detector that auto-collapsed the dashboard back to overlay mode whenever another window came to the front, which has been removed so both platforms behave the same: fullscreen is left only via an explicit user action (keybind/voice), never automatically. The small idle overlay widget's click-through is applied immediately in `__init__` on both platforms now — Linux via Qt's `WA_TransparentForMouseEvents`/`WindowTransparentForInput` attributes, Windows via the `_set_win32_click_through` helper's raw `WS_EX_TRANSPARENT` toggle (Qt's attribute doesn't reliably apply on Windows combined with `WindowStaysOnTopHint`+`Tool`) — previously the Windows toggle only ran inside the `set_ui_mode("set_overlay")` transition, so it wasn't click-through until the first fullscreen↔overlay round-trip.
- **ConfigLoader** (`src/utils/clConfigLoader.py`) enforces JSON Schema validation (`config/intents_schema.json` etc.) rather than tolerating malformed config — per `.agents/AGENTS.md`, don't add legacy-compat fallbacks here, keep configs on the strict modern schema.
- **UI** (`src/clUI.py`, ~1900 lines, PyQt6, plus `src/ui/*Widget.py`) is a separate desktop app that talks to the rest of the system purely over MQTT (`paho-mqtt`) — treat it as just another decoupled client, not part of the daemon process.
- **State persistence is mid-migration to Redis** (`src/utils/clRedisClient.py`, pooled client keyed off `REDIS_HOST`/`REDIS_PORT`/`REDIS_DB` in `.env`) — see `tests/test_redis_migration.py` for the target shape when touching persisted daemon/UI state.
- The live daemon's SLM model path is `config/core.json` → `settings.slm_settings.model_path`, independent of the hardcoded `MODEL_PATH` in `training/tools/benchmark_slm.py` — keep both pointed at the same GGUF when swapping in a newly trained model.
- Both `slm_settings` and `reply_slm_settings` in `core.json` also carry a `model_url` — if `model_path` isn't present under `models/` at boot, `nlp/clSLM.py`'s `ensure_gguf_exists()` downloads it from there (e.g. a Hugging Face `resolve/main/...` link). Neither GGUF is a stock model, so there's no hardcoded fallback URL; an empty `model_url` with a missing file just disables that engine with a clear log message instead of crashing.
- **Claude voice bridge** (`src/clClaudeBridge.py`): mirrors a real `claude` CLI session into the ecosystem. Voice commands routed by `clDaemon.py`'s Claude-bridge regex (see `route_voice_command`) land on `jarvis/claude/question`; the bridge types that text into a persistent `claude` session as if typed at the keyboard, and mirrors that session's screen back out on `jarvis/claude/screen` for a dashboard widget. Two backends share one `ClaudeSessionBase` (`src/utils/clClaudeSession.py`) holding everything OS-independent — busy/prompt detection, first-run auto-answers and their retry, stall detection, sign-in URL opening, session settings files, and config-dir/`--continue` logic — while each backend owns only spawn, send text, send raw keys, obtain screen text, alive check, and stop. `src/utils/clPtyBridge.py` (`ClaudePtyBridge`) is the Windows backend: ConPTY through `pywinpty`, rendered to plain text through `pyte` since ConPTY only hands back raw ANSI. It spawns the native `claude.exe` bundled inside the npm-installed CLI directly rather than the `claude.cmd` shim — a `.cmd` file's arguments don't survive being spawned straight through `CreateProcess` under ConPTY, so `--continue` was silently getting dropped. `src/utils/clClaudeTmuxBridge.py` (`ClaudeTmuxBridge`) is the Linux backend: tmux resolves the ANSI screen itself (`capture-pane -p -J`), so no terminal-emulation library is needed; a detached `tmux new-session` outlives the bridge process, so a bridge crash/restart reattaches to the same session (`has-session`) instead of losing it, and `pipe-pane` into a FIFO drives event-driven screen updates instead of polling. AUTO_ANSWERS tokens are backend-neutral (`"DOWN ENTER"`, `"ENTER"`); each backend's `_send_control_keys()` maps them to its own encoding — ConPTY escape bytes on Windows, tmux key names (`.title()`'d, e.g. `"Down Enter"`) on Linux. Both backends launch with `--continue` once a prior conversation exists (see below), so a crashed/restarted session recovers its full history rather than starting blank.
  - **Isolated config directory, not the default `~/.claude/`.** The bridge sets `CLAUDE_CONFIG_DIR` (documented in Claude Code's own auth docs) to `data/claude_bridge_config/` (gitignored — it holds real credentials) before spawning. This exists specifically because sharing `~/.claude/` with whatever interactive `claude` session a developer happens to have open (e.g. one editing this very repo) triggers a documented lock-contention hang during login (github.com/anthropics/claude-code issues [#91987](https://github.com/anthropics/claude-code/issues/91987), [#63007](https://github.com/anthropics/claude-code/issues/63007)) — a real, reproduced issue during this feature's own development, not a hypothetical. A dedicated config dir means the bridge's process never touches the same files as any other `claude` session at all.There is deliberately no `.env`/Settings credential like Tapo's or Spotify's: `CLAUDE_CODE_OAUTH_TOKEN` only applies to headless `-p` calls and the interactive session ignores it (all `CLAUDE_CODE_*` vars are stripped from the spawn env anyway). The sign-in lives in the config dir instead — see `--setup` below.
  - **Every process spawn strips inherited `CLAUDE_CODE_*` env vars** before launching. `child_env = os.environ.copy()` used to carry these straight through from whatever shell launched the ecosystem (e.g. a Claude Code session doing dev work on this very repo) — the spawned `claude` then saw itself as a nested child session and silently disabled transcript saving, which `--continue` itself depends on to have anything to resume.
  - **`--continue` is only passed once a real prior conversation exists.** `claude --continue` hard-errors ("No conversation found to continue") and exits immediately if `<config dir>/projects/` doesn't exist yet — true for every first launch against a fresh config dir. `ClaudeSessionBase._should_continue()` checks for that directory (shared by both backends) and the flag is omitted until a real session has actually been recorded there.
  - **First-run screens are auto-answered** by `ClaudeSessionBase._maybe_auto_answer()` off the shared `AUTO_ANSWERS` rule table (marker text on screen → backend-neutral token): the theme picker and login-method menu (both already highlight the right option — Dark / "Claude account with subscription" — so plain `"ENTER"`), every "Press Enter to continue" (login success, security notes), and the "trust this folder?" menu. The trust menu is an arrow-key list defaulting to `❯ No, exit`, so typing text + Enter would confirm "No" and quit; it needs a down arrow plus Enter (token `"DOWN ENTER"`) sent via `send_keys()` (raw control sequences, unlike `write()` which types a line and submits it) — on Windows this is the application-mode escape `\x1bOB\r` (not the normal-mode `\x1b[B` — this TUI runs with application cursor keys enabled), on Linux it's tmux's own `Down`/`Enter` key names, which tmux resolves to the right escape itself. Back-to-back screens with the same marker are told apart by the whole screen text, and an Enter dropped while the TUI was redrawing (same screen, no new output for 3s) is retried up to 3 times. Trust state persists in the config dir, so it doesn't recur.
  - **Speech is the bridge's job, not the session's.** A `Stop` hook (`src/utils/clClaudeStopHook.py`) receives the finished turn's `last_assistant_message` from the CLI and publishes it to `jarvis/claude/reply`; `clClaudeBridge.py` strips code/tables/markdown/URLs (`speakable_text`, capped at 800 chars on a sentence boundary), and publishes to `jarvis/sys/speak` with `claude_session: true`, plus `request_reply` when the answer ends in a question so the daemon re-opens the mic for a spoken answer. It deliberately does *not* set `ignore_silent`, so silent mode mutes it (and makes audible-free testing possible). The hook and an appended system prompt (`--append-system-prompt-file`) are passed per launch via `--settings`/CLI flags generated into the config dir, so they never touch a developer's own `claude` sessions. Because the model still sometimes ran the repo's standing speak command itself (doubling every answer), a `PreToolUse` hook (`--block-speak`) refuses any Bash command mentioning `jarvis/sys/speak` in the bridged session, and the standing instruction above defers to the bridge.
  - **Stall watchdog and readiness.** `ClaudeSessionBase.process_screen()` (fed a fully-resolved screen by either backend) tracks two flags off every snapshot: busy (`esc to interrupt` in the footer) and at-the-idle-prompt (a `❯` row bracketed by horizontal rules — menus reuse `❯` but have no rules). A busy session that emits no bytes for 60s is hung (a working one redraws its spinner constantly): `on_stall` fires, and `clClaudeBridge.py` kills the session, restarts it (`--continue` resumes the conversation), waits for the idle prompt, and re-sends the last question once — the retried question shows up twice in the transcript, which is accepted over dropping it. The same readiness wait gates the first injection into any freshly started session, since input typed while the TUI is still booting gets dropped. Root cause of the underlying hang (first found on Windows) was never determined (process alive, no children, no output); this is recovery, not a fix.
  - **Sign-in: via the dashboard widget, or one-time via `python src/clClaudeBridge.py --setup`.** The bridge authenticates from `data/claude_bridge_config/.credentials.json` (written by a real browser sign-in), not from any env var. Missing credentials are no longer a hard blocker on `ClaudeBridgeService.run()` — the live service starts the session anyway (`force_fresh=True` on that first start only, so it never silently reattaches to a stale session an earlier aborted attempt left behind, e.g. one stuck on an expired OAuth prompt): the trust/theme/login screens auto-answer themselves, the sign-in URL opens in the browser automatically, and the dashboard's Claude widget (mirroring `jarvis/claude/screen`) shows the resulting `Paste code here` prompt for you to paste the code into directly, via `jarvis/claude/question`. `--setup` (also `force_fresh`-guarded) remains for a pure-terminal alternative — running it while the live bridge is *also* running is still the documented lock-contention risk (a second `claude` process against the same config dir; the cause of this feature's very first stall on Windows), so use one path or the other, not both at once. The browser authorization click itself can never be automated.
  - **System requirements, both OSes: the `claude` CLI itself, plus `tmux` on Linux.** Neither is a `requirements.txt` entry (that file is pip-only), so `boot.py` auto-installs both, best-effort and non-fatal like its other optional-feature setup: `_ensure_linux_system_packages()` apt-installs `tmux` and `npm` on Linux (extending the same dict that already covers `pactl`), and `_ensure_claude_cli()` runs on both OSes — installing Node/npm via `winget` first if missing on Windows (same tool `clUpdater.py` already uses for app updates; the freshly-installed dir is added to `os.environ["PATH"]` directly since a winget install's PATH update doesn't reach the already-running boot process), then `npm install -g @anthropic-ai/claude-code` either way. A machine with no `apt-get`/`winget` (or where either step fails) just gets a clear message to install manually; either way `ClaudeTmuxBridge.start()`/`ClaudePtyBridge._resolve_claude_binary()` still check with `shutil.which()` before spawning and raise a clear `FileNotFoundError` naming whichever is missing, rather than the ecosystem supervisor silently respawning a service that can't work.

**Standing instruction for any Claude Code session working in this repo**: when the JARVIS ecosystem is running live, speak a short, one-sentence summary of what you did or what's needed next at the end of every turn by publishing to `jarvis/sys/speak`, unconditionally — not only when reached through the voice bridge. The one exception: if your system prompt says the host application already reads your answers aloud (the bridged voice session), do not run this; the bridge speaks every final answer itself and would double it:
  ```
  python3 -c "import paho.mqtt.publish as publish, json; publish.single('jarvis/sys/speak', json.dumps({'text': '...', 'ignore_silent': True}), hostname='localhost')"
  ```

## Working in this repo

- **On Windows every service shows up as two `python` processes — that's expected, not a leak or a duplicate.** The venv is built from the Microsoft Store Python, so `.venv\Scripts\python.exe` is a ~270 KB launcher stub (~10 MB each, ~140 MB across the ~14 services) that spawns the real `python3.12.exe` as its child, and the *child* does all the work (e.g. clDaemon's holds ~1 GB of models). The launcher ties the child's lifetime to its own, so `proc.terminate()` on the stub (what `clJarvis.py`'s `stop_native` and `boot.py`'s sweep do) takes both down. When killing something by hand, kill the stub with `taskkill /PID <pid> /T /F` and never the child alone — the supervisor just respawns it — and match on the script name, not on which interpreter path is shown.

- `models/` (~2GB of GGUF + faster-whisper HuggingFace cache blobs) is gitignored — never read or grep into it.
- `data/` holds only gitignored per-user runtime state (`todos/`, `reminders/`, `alarms/`, `events/`, `ui_state.json`) — none of it is a fixture, don't treat its contents as canonical. The versioned training datasets live separately under `training/data/`.
